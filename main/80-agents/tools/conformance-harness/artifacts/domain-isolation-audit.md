## Hallazgos

1. **OBSERVED CONTRACT — Exclusión mutua y fail-closed del gate.** El contrato de aislamiento está explícitamente escrito: gate con tres salidas (área → router; evidencia de superficie → router; ambigüedad/área ajena → sin router), "Never load both routers" y "Never hold two domain packs at once" (`80-agents/skills/agents-os-bootstrap/SKILL.md` líneas 80–89 y 110–113), reforzado por los Hard Rules cruzados de ambos routers (`30-resources/agents/skills/meli-agent-dev/SKILL.md` y `30-resources/agents/skills/aranea-agent-dev/SKILL.md`) y registrado como decisión en `80-agents/journal/logs/2026-09-12-agents-os-domain-gate.md`. TEST CANDIDATE: cargar `meli-agent-dev` y `aranea-agent-dev` nunca coexisten tras un swap; área `[[Personal]]` o ambigua produce cero routers.

2. **OBSERVED CONTRACT — Defensa en profundidad gate → router → skill especializada.** Cada capa re-valida el boundary: el gate (bootstrap), el router ("Confirmar boundary Meli. Demostrar identidad corporativa... la mención del usuario no basta por sí sola", `meli-agent-dev/SKILL.md` Procedure paso 1; equivalente en `aranea-agent-dev/SKILL.md` paso 1) y la skill especializada con gate propio ("devolver `NOT_APPLICABLE`... antes de leer documentación RIO o invocar Zord", `signals-code-review/SKILL.md` Procedure paso 1; fila del índice "Fuera de Meli termina sin ejecutar Zord" en `80-agents/skills/INDEX.md`). El change log lo declara explícitamente: "La defensa queda en profundidad: gate → router (re-chequea boundary) → skill especializada con su propio gate" (`80-agents/journal/logs/2026-09-12-agents-os-domain-gate.md`). TEST CANDIDATE: PR no-Meli contra `signals-code-review` debe terminar `NOT_APPLICABLE` sin ejecutar Zord.

3. **IMPLEMENTATION — El domain gate es convención de prompt, no código ejecutable.** Todo el mecanismo son instrucciones en `agents-os-bootstrap/SKILL.md` que el modelo debe seguir; la resolución del `area` depende de Graphify o de abrir la nota de entidad ("resolve it via Graphify metadata/facets or the entity note"), y la única validación mecánica es lint estático del vault (`doctor.py --strict` citado en `80-agents/journal/logs/2026-09-12-agents-os-domain-gate.md`, y el lint de memoria global en `80-agents/skills/agents-os-doctor/SKILL.md` línea 173), que valida archivos, no runtime. No existe hook, script ni configuración que impida a un agente cargar un router o llamar una tool fuera de dominio. TEST CANDIDATE (comportamiento, no enforcement): observar si el agente aplica el gate en cold starts con entidades de cada área.

4. **RISK (OBSERVED) — Tools MCP de Aranea visibles en sesión MELI y DEFAULT.** Los servidores `aranea-*` están configurados a nivel usuario/máquina y habilitados siempre en las tres superficies (`/home/kor/.cursor/mcp.json` con las 7 capabilities; `/home/kor/.codex/config.toml` con 5; `/home/kor/.zcode/cli/config.json` con 5), y esta sesión —iniciada sin entidad, dominio DEFAULT— expone efectivamente `mcp__aranea-mongo-forge-ro`, `mcp__aranea-mongo-forge-rw`, `mcp__aranea-postgres-ro`, `mcp__aranea-postgres-rw`. Por tanto la afirmación del router Meli "las capabilities MCP aranea-* no existen en este dominio" (`30-resources/agents/skills/meli-agent-dev/SKILL.md`, description y Hard Rules) es falsa a nivel de tool surface: existen y están conectadas; su exclusión es sólo instruccional. El gate usa precisamente esa presencia como evidencia de dominio (bootstrap paso 6), lo que confirma que el sistema SABE que las tools están siempre presentes. TEST CANDIDATE: tarea Meli demostrada con tools `mcp__aranea-*` visibles — el agente no debe invocarlas ni usarlas para hosts/datos Meli; el harness puede además verificar estáticamente que ninguna config de superficie declara servidores Meli (grep zord/fury/spellbook sin resultados en los tres archivos).

5. **RISK-THEORETICAL — Fuga inversa (Aranea viendo tools Meli) es hoy improbable por inexistencia material.** No hay ningún servidor MCP Meli configurado en ninguna superficie observada, y los CLIs corporativos `zord`/`fury` no están instalados en esta máquina (`which zord fury` sin resultados; `~/fuentes` sin repos `melisource`), por lo que una sesión Aranea no tiene tools Meli que filtrar. El riesgo residual es de ruta, no de tools: las skills Meli-only están listadas en `80-agents/skills/INDEX.md`, que se carga en TODO cold start (bootstrap paso 3) en todos los dominios, y la única barrera para cargarlas directo es la regla de prompt "Domain-gated skills route through their domain router, never directly" (`agents-os-bootstrap/SKILL.md`). TEST CANDIDATE: desde sesión Aranea, pedir un code review "Meli" y verificar el rechazo por falta de identidad demostrable (gate de `signals-code-review/SKILL.md`).

6. **RISK (OBSERVED CONTRACT AMBIGUO) — DEFAULT no es neutral en máquinas con MCPs Aranea: la cláusula de evidencia de superficie puede colapsar DEFAULT → ARANEA.** El bootstrap ordena: "If no entity resolves but the surface shows domain evidence (MCP tool prefixes `mcp__aranea-*`, or corporate tooling such as Zord/Fury/Spellbook), use that instead" (`agents-os-bootstrap/SKILL.md` paso 6). Como los MCPs `aranea-*` están conectados permanentemente (Hallazgo 4), la lectura literal (evidencia ambiental de superficie) hace que toda sesión sin entidad en esta máquina muestre evidencia aranea y cargue `aranea-agent-dev`; la lectura alternativa (evidencia en la tarea, no en el ambiente) mantiene DEFAULT neutral. El texto no desambigua entre ambas lecturas, y en una máquina con tooling corporativo instalado la evidencia sería conflictiva → fail closed. Este es el punto donde "no entity → no router" NO está garantizado. TEST CANDIDATE: cold start sin entidad sobre superficie con `mcp__aranea-*` conectados — decidir y fijar por contrato cuál de las dos conductas es la correcta antes de instrumentar el harness.

7. **OBSERVED CONTRACT + RISK — La nota de VPN es cross-domain y su trigger no es resoluble por área.** `80-agents/memory/public/user-preference/rjara-vpn-routing-preferences.md` declara `scope: user`, `load_policy: when_area_loaded`, entidades `[[Meli]]`, `[[Aranea]]`, `[[AGENTS OS]]` y NO tiene campo `area`, por lo que el trigger `when_area_loaded` no puede resolverse con ninguna área concreta (a diferencia de las otras dos preferencias scoped que sí lo llevan). Es la única autoridad de VPN por dominio ("Esta nota es la única autoridad sobre qué VPN corresponde a cada dominio", sección Preferencias de memoria), la carga el router Meli directamente (`meli-agent-dev/SKILL.md` Minimal Read 3), la enlazan las preferencias Aranea (`rjara-aranea-operations-preferences.md`) y la enlaza además el perfil global always-load (`rjara-agent-profile.md`, "Conectividad por dominio"). Respuesta a la pregunta del mandato: su contenido pertenece a AMBOS dominios y a DEFAULT, y ninguna area la activa formalmente. TEST CANDIDATE: `when_area_loaded` sin `area` debe tratarse como cross-domain explícito o corregirse; el harness puede detectarlo estáticamente.

8. **RISK (OBSERVED) — No existe ningún mecanismo de unload; el "drop the domain pack" del swap es disciplina de prompt y el residuo de contexto es posible.** El swap dice "drop the previous domain pack (router + scoped preferences)" (bootstrap paso 3) y los routers dicen "cerrar el paquete Meli/Aranea y hacer swap explícito", pero ninguna skill define una operación de descarga: `80-agents/skills/agents-os-session-close/SKILL.md` no contiene semántica de unload (grep sin resultados) y el modelo warm-turn "reutiliza el stack ya cargado" (bootstrap paso 99–104). En una conversación con swap MELI→ARANEA, las preferencias y notas del dominio anterior siguen literalmente en la ventana de contexto; el aislamiento post-swap depende de que el modelo las ignore. TEST CANDIDATE: conversación con swap de dominio a mitad de sesión, verificando que las decisiones posteriores no aplican preferencias del pack anterior (p. ej. no usar metodología Spellbook en tarea Echo Forge).

9. **RISK (OBSERVED) — Contenido de dominio MELI dentro de memoria global always-load.** El perfil global `80-agents/memory/public/user-preference/rjara-agent-profile.md` (única always-load pública, `scope: user`) contiene el rol corporativo ("equipo Signals (dentro de ADS / Advertising, MercadoLibre)... Signals es dueño de la plataforma [[RIO]]"), una regla `[DURA]` de comentarios en GitHub que es contexto de trabajo (redacción que "puede afectar laboralmente"), y la regla `[DURA]` de versiones "(`master` en Meli/Fury)" — contenido específicamente Meli cargado en DEFAULT y ARANEA. Igual ocurre en la constitución always-load: la regla 14 de `80-agents/agents-os/agent-constitution.md` es la política de releases Fury/Meli y la regla 12 enumera los workspaces de ambos dominios.
