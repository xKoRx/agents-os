## 4. R04 — Identidades, receipts y retención

- **Scope de `history_id`:** EXTERNO (estable, asignado por el productor). Identidad de historia = PK `(registry_namespace, strategy_version_ref, producer_writer, history_id)` con `producer_writer` FIJO al crear y parte de la identidad: dos productores del mismo namespace+versión que usen el mismo id local NO colisionan (son historias distintas/alternativas legítimas); mismo writer + mismo id con contenido distinto → 409. Dedup de contenido: `history_digest` igual entre alternativas se muestra como información (alternates idénticos), no cambia identidad. El contexto MM vive en `strategy_history_selection` (principal/alternativas por (namespace, version_ref, contexto)), no en la identidad. No se crea otro registro de estrategias.
- **Receipts:** tabla NUEVA `echo.strategy_ingestion_receipts` con el patrón de promotion_records (`idempotency_key` sha256 por (namespace, writer, key), `request_digest`, status, punteros de resultado, `accepted_at`, replay resuelve receipt antes de contrastar head). `promotion_records` NO se generaliza: su contrato operacional de promociones queda intacto.
- **Retención de inputs (D14 concreto):**
  - Contenido fijado: body canónico aceptado (NDJSON comprimido, los bytes exactos que producen `history_digest`) + `contract_version` + digest de receipt.
  - Durable: write-ahead — PUT digest-addressed idempotente al artifact store existente (FS local DEV / MinIO) ANTES del commit; la transacción PG (revision + receipt + head) referencia (store, digest, size). El commit es la autoridad; commit sin artefacto es imposible por orden.
  - Fallo entre storage y commit: artefacto huérfano sin referencia, elegible para GC SÓLO por falta de referencia (nunca por edad); cero inconsistencia.
  - Reconstrucción tras PUT: revisiones append-only con head pointer; resultado N = artefacto(digest revisión N) + versión de algoritmo + `config_digest`.
  - Protección: GC sólo digests sin referencia en revisiones (activas e históricas) y manifiestos de jobs; toda revisión referenciada por un resultado vigente o job histórico se protege; no se retienen revisiones sin valor indefinidamente (head + revisiones de resultados vigentes + política N configurable).
- **Autoridades de recovery preservadas:** journal REAL y checkpoint/estado del runtime siguen siendo la autoridad operacional de recuperación; la historia analítica y la proyección PG V4 son derivados de consulta, nunca autoridad (coherente con D2-04 R14). Ni historia ni proyección sustituyen esas autoridades.
