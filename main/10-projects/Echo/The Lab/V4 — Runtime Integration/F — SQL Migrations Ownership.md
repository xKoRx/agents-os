# F — SQL Migrations Ownership

## Propósito

Especificar la persistencia aditiva del recorrido Forge → Echo operacional → historias → LAB, con identidad compuesta, revisiones reproducibles y publicación atómica. El runtime y venue conservan sus autoridades: PostgreSQL proyecta hechos y conserva control/derivados analíticos; jamás recupera Operation/MMState ni decide trading desde una curva. Diseño Shot 1; no es SQL aplicado ni certificación de ambiente.

### 3. Ledger, checksum y ejecución segura

Se reemplaza explícitamente el intento histórico de auto-registro de `file_sha256` dentro del propio archivo: un archivo no puede incluir su hash exacto sin autorreferencia circular. El runner existente calcula SHA256 sobre los bytes exactos del `.up.sql` o `.down.sql` leídos, antes de ejecutarlos; build/review conserva un manifest externo `(id,direction,path,sha256,source_sha,dependencies,catalog_signature)`, sin incluir su propio checksum dentro del SQL. El SQL no inserta hashes constantes autorreferentes. No regenerar archivos ya aplicados.

Delta mínimo en `v3/toolkit/cmd/apply-migration/main.go`: validar flags/path/id/direction/manifest; requerir parámetros explícitos de conexión sin defaults de credenciales; fijar `application_name`, `lock_timeout=5s`, `statement_timeout=120s`; `BeginTx(READ COMMITTED)` → `pg_advisory_xact_lock` global de migraciones → consultar existencia de ledger: si ausente sólo se permite 067 y se ejecuta su DDL para crearlo dentro de ESTA transacción; si presente comparar ledger/dependencias y firmas de objetos antes de ejecutar el archivo sin BEGIN/COMMIT internos → insertar ledger+evento desde Go con checksum calculado → commit. Up no usa `CREATE INDEX CONCURRENTLY` dentro de transacción; se crean tablas nuevas antes de traficarles datos, por lo que no es necesario. Locks timeout dejan rollback íntegro y resultado retryable; ALTER sobre tabla antigua se realiza sólo en ventana propia y vuelve a intentar tras nueva lectura, sin matar sesiones ajenas.

`echo.lab_migration_state(migration_id int PK, up_sha256 text NOT NULL CHECK digest_regex, down_sha256 text NOT NULL CHECK digest_regex, source_sha text NOT NULL, state text CHECK IN('APPLIED','ROLLED_BACK'), applied_at timestamptz NOT NULL, applied_by text NOT NULL, effects_signature echo.v4_digest NOT NULL)`; `echo.lab_migration_events(event_id bigint identity PK, migration_id int NOT NULL, direction text, file_sha256 text CHECK digest_regex, actor, event_at, catalog_signature, outcome)` es auditoría append-only. Reapply mismo id+checksum+firma válida devuelve ALREADY_APPLIED sin DDL; mismo id con otro checksum da `MIGRATION_CHECKSUM_CONFLICT` antes de DDL. Ledger presente con efectos incompatibles da `MIGRATION_DRIFT`; objeto preexistente no se adopta por `IF NOT EXISTS` sin validar columnas/constraints/owner. Migración fallida no deja fila APPLIED ni efecto parcial. Commit incierto se resuelve leyendo ledger y firma antes de retry.

Para bases históricas sin ledger se registra sólo `OBSERVED_EFFECTS` en inventario de preflight por 001–066, con fecha/owner/firma; jamás se inventa file checksum ni APPLIED. Una afirmación de otra ventana como “066 no aplicada en DEV” sigue siendo evidencia histórica; esta SPEC no la recertifica. 067 exige firmas mínimas de registro y journal esperadas, admite 066 presente o ausente. Down de 067 nunca borra auditoría: conserva tablas ledger/events, cambia estado y registra el intento; infraestructura de auditoría es un residual documentado, no pérdida de reversibilidad de negocio.

### 4. Tipos SQL, tiempo exacto y reglas comunes

`ns` abrevia columna física `registry_namespace text NOT NULL`; todas las tablas tenant tienen ns. `D` abrevia `echo.v4_digest` (text, regex `^sha256:[0-9a-f]{64}$`); `ID` es text UTF-8 no vacío ≤256 bytes salvo contrato vigente más estricto; refs nuevas usan `wire.HashTagged`/`wire.Digest` de [[A — Runtime CURRENT TARGET]] y [[C — Histories Revisions Economy]]. Campos requeridos por DTO A–E y campos de identidad/digest/estado de control se declaran NOT NULL; sólo son nullable ausencias explícitas del contrato (NULL/?/opcional, timestamps de cierre de ciclo abierto, resultado aún no calculado, lease libre o error ausente). Cada CHECK de conjunto opcional comprueba presencia completa o ausencia completa, nunca depende de que SQL UNKNOWN sea rechazado. Nunca usar otro serializador SQL para calcular identidad. Hash se valida/recomputa en el servicio Go y se conserva el body canónico original; JSONB sirve para consulta y no define los bytes canónicos. Reject unknown fields y duplicate keys antes de persistir.

`N` es dominio sobre numeric SIN typmod, finito, `scale(VALUE)<=18` y `abs(VALUE)<10^20`, equivalente de rango a numeric(38,18) sin el redondeo implícito de un cast previo. `CK_DECIMAL_EXACT` valida también canonical string original con wire y rechaza overflow/scale; evidencia monetaria nunca se redondea para caber. Valor `0` es dato válido; NULL significa ausencia con reason, jamás COALESCE económico a cero/USD/Q. `derived-fixed24-half-even.v1` es la política única de derivados D: `B_i` y cada delta se cuantizan explícitamente HE24, las sumas usan esos decimales24 exactos y la cota de redondeo se acumula hacia arriba. Guardar derivados en dominio `lab.v4_calc_decimal` sobre numeric SIN typmod, finito, scale≤24 y abs<10^52; rango equivalente a numeric(76,24) sin cast silencioso. Campos `value_calc`, `delta_calc`, `peak_calc`, `drawdown_calc`, `rounding_error_bound`, `value_display12`, `numeric_policy_digest`; CHECK rounding_error_bound≥0. Las APIs usan strings canónicos. Rat es opcional/transitorio acotado: numerador/denominador de un decimal FINITO q24, fracción reducida con denominador divisor de10^24; nunca expansión racional de reinversión con O(n²) bits. Alcanzar límite numérico o frontera causal no resuelta devuelve insuficiencia explícita, no overflow ni clamp. Fórmulas métricas/sqrt usan la política HE24 de D y scores conservan float64/bits de E; no mezclar estos tres dominios numéricos.

`Seq` int64 SQL bigint positivo, ingresado como entero JSON seguro ≤2^53−1; `effect_index` int>=0. La secuencia física del owner admite cero sólo en la proyección de envelopes actuales cuyo contrato lo permite; nuevas revisiones/config/fencing son >0, head vacío es 0. Desbordamiento falla explícito, no wrap/reset. Currency text cumple `^[A-Z]{3}$`, con status/evidence; sin FX implícito.

PostgreSQL timestamptz conserva microsegundos, mientras los DTO aceptan RFC3339Nano: guardar toda TimeEvidence canónica como JSON y `*_at_text`/`*_epoch_ns numeric(30,0)` exactos para orden económico. `*_at timestamptz` es auxiliar de display/índice grueso; nunca lo reserializar para hashes ni usar como desempate causal único. SQL ordena por epoch_ns y claves causales. Leases/applied_at/created_at de control usan timestamptz y reloj DB. UNKNOWN/NOT_APPLICABLE exigen valor económico NULL+motivo; PROVEN exige valor+evidence. No rellenar construction_at con cutoff/receipt.

### 6. execution: proyección, deduplicación y correlación

`execution.reference_cycles(ns,reference_cycle_id D PK,version_ref,run_id,run_mode,reference_account_id,binding_ref,config_revision,source_family,opening_source_id,content_digest,evidence_ref)` referencia versión/run/cuenta/binding exactos. `source_correlations` PK `(ns,run_id,source_family,source_id,account_id,account_role)` apunta a ese ciclo y `source_operation_ref D`, con runtime_operation_id nullable, binding/config/version y evidence/digest. Source family admite los valores A; varios order/fill IDs pueden enlazar un ciclo. Primera vinculación sellada, replay mismo digest converge, conflicto entra a cuarentena sin merge heurístico. Cuenta master y copia siguen hechos distintos.

`operation_facts(ns,run_id,owner_ref,owner_event_seq bigint,effect_index int,kind, fact_id D, payload_digest D, canonical_artifact,received_at)` PK `(ns,run_id,owner_ref,owner_event_seq,effect_index)` y UNIQUE `(ns,fact_id)`. ### 9. Transacciones, locks, fencing y errores

Orden global para todos los writers/publishers: advisory guards de creación ordenados por ref → filas registry metadata/history/selection/composition en orden `(kind,ref)` → analysis targets ordenados → ranking targets ordenados → read pointers. Un writer no toma target lock antes del input lock correspondiente. Advisory xact bigint proviene de primeros64 bits del Digest de lock-domain+ns+entity; colisión sólo serializa de más, identidad siempre se comprueba con PK completa. No session lock ni lock de scope global por cada cálculo.

`HISTORY_ACCEPTED` usa READ COMMITTED: validar DTO/artifact → lock advisory de HistoryKey ausente y row lock existente → reconsultar receipt → comparar CAS `(revision,digest)` → insertar N+1/header/operations/movements/changes+receipt+dirty → actualizar head condicional y commit. Receipt lookup precede CAS, replay exacto retorna receipt original aunque head avanzó. PUT sin precondición428; header/body contradictorio400; stale CAS412; idempotency mismo key otro body409; economics/semantic422. Todos los histories de POST≤8 se bloquean por history_ref ordenado en una transacción. Unknown shape400, límite413, no scope403/404 según API, DB/artifact503; rechazo sin receipt parcial. CAS nuevo requiere body/key nuevos; timeout conserva key y GET receipt antes de retry.

`ANALYSIS_PUBLISH`: claim READ COMMITTED corto con SKIP LOCKED sólo de cola, batch≤2, lease60s/heartbeat20s/token incrementado; snapshot input RR corto pinneado; compute fuera de DB; publicación READ COMMITTED con locks de TODOS los heads/policies y target en orden global; comprobar manifest/spec/catalog/calendario/metadata+desired_seq+lease_owner+token y `lease_until>clock_timestamp()`; insertar bundle completo+outputs+current pointer+attempt completion en la misma transacción. Heartbeat usa la misma condición y reloj DB; expirado no revive con token antiguo. Update pointer condicional afecta una fila o rollback; worker viejo no promueve aunque haya calculado bien. Header publicado es inmutable; obsolete attempt conserva evidencia fuera del pointer. Si un perfil falla técnicamente no promueve ningún perfil; falta económica terminal puede publicar estado insuficiente junto a los hermanos.

`COHORT_PUBLISH` usa mismo protocolo lease60/20/fencing y lock de TODOS los input heads/targets y ranking target, valida vector+membership completo y snapshot generation de cada miembro, inserta todas las rows/extrema/components y pointer en una transacción. Cualquier cambio de miembro invalida cohorte completa y se reencola; no parchea su score con extremos antiguos. Cambio CAS expuesto por API412; conflicto de determinismo/identidad409 permanente. No se calcula mientras se sostienen esos locks ni se confía en un SELECT previo sin serializar contra escritores. Deadlock40P01/serialization40001 son retryable inspeccionando estado durable primero; error ACK de commit se concilia por receipt/generation/attempt y mismo digest.

Retries análisis D 1/2/4/8/16s máximo5 por desired_seq, luego FAILED_RETRYABLE visible y manual retry conservando última generación; shape/digest/algoritmo/invariante inválida FAILED_PERMANENT. Ningún caso restaura runtime desde execution.operations, histories o curva.
