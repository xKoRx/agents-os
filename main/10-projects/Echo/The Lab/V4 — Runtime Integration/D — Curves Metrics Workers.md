# D — Curves Metrics Workers

## Propósito

Contrato ejecutable de diseño para cuatro perfiles económicos, métricas reproducibles y workers analíticos sobre la rama runtime vigente. Implementa las decisiones D09/D10/D11/D16 y la autoridad de D24, conserva la economía y revisiones de [[C — Histories Revisions Economy]] y entrega a [[E — Rankings Shared Go Parity]] los mismos resultados que explican el detalle. Todo lo prescrito como TARGET es trabajo Shot 2; ningún diseño de esta nota acredita implementación o pruebas físicas.

### 2. API pura, registro y tipos de resultado TARGET

Superficie pura nueva en `Echo:v3/sdk/lab/analyze`: `BuildTimeline(HistorySnapshotSet, SelectionRevision, EconomicCut) -> Timeline`; `CurveFactory.New(ProfileDescriptor, CanonicalConfig) -> CurveAlgorithm`; `CurveAlgorithm.Compute(context.Context, Timeline) -> CurveResult`; `MetricFactory.Compute(CurveResult, Timeline, MetricSpec) -> MetricSet`. El contexto sólo cancela; no entrega reloj/config, DB, red ni random. Inputs se copian o son inmutables; jamás se muta un big.Rat compartido entre presupuestos/puntos. Toda lectura externa ocurre antes de entrar a estas funciones. Los servicios, worker y herramientas de comparación usan estas mismas funciones; no hay fórmulas distintas en SQL/front/Forge adapters. El kernel compartido de ranking entre Echo/Forge lo fija E y consume este MetricSet.

`ProfileDescriptor = {profile_id, algorithm_version, config_schema_version, unit_kind, requirements[], default_enabled, descriptor_digest}`. IDs públicos completos: `recorded_money.v1`, `r_net_cumulative.v1`, `normalized_10k_open_balance.v1`, `normalized_10k_initial_balance.v1`; `algorithm_version="1"` identifica el código económico congelado de cada uno. Cambio semántico exige otro profile_id o algorithm_version y nunca sobrescribe una generación anterior. Schema de config desconocido o campo no reconocido => 422 `PROFILE_CONFIG_INVALID`; ID desconocido => 422 `PROFILE_UNSUPPORTED`. No hay AUTO ni fallback al perfil que sí tenga datos.

`DefaultRegistry()` construye una lista ordenada, registra exactamente esas cuatro factories, rechaza duplicados al arranque y devuelve un catálogo con descriptors. La misma lista genera las specs default y la UI: añadir una factory registrada genera su job automáticamente sin editar switches de worker o front. Por defecto se calculan los cuatro perfiles tras cada revisión aceptada, incluso para publicar estado insuficiente en uno de ellos. La versión/digest del catálogo forma parte del desired manifest; cambiar catálogo encola los targets afectados. Las configs personalizadas son specs distintas, no edits del preset.

`Config` normalizada explícita: `{initial_capital:"10000", risk_fraction:"0.01", fx_policy_id:"NO_FX", causal_order_policy:"timestamp-batch-or-proven-total.v1", precision_policy:"rational-exact.v1", display_policy:"display-half-even-12.v1"}`. C0 y r son configurables para perfiles normalizados: C0>0, 0<r≤1, decimales canónicos de C; capital virtual en unidad `VIRTUAL_CAPITAL`, sin USD implícito. Money/R rechazan initial_capital/risk_fraction como config económica propia en vez de aceptar claves ignoradas; su config contiene sólo políticas aplicables. La respuesta siempre muestra la config efectiva y digest, incluidos defaults expandidos.

`CurveSpec = {namespace, target_ref, target_kind:HISTORY|SELECTION|STATIC_COMPOSITION, profile_id, algorithm_version, config_digest, origin_at, origin_policy, economic_as_of, knowledge_mode, knowledge_cutoff?, input_manifest_digest}`. `origin_policy=HISTORY_START` procesa todos los ciclos seleccionados desde su comienzo probado; `FLAT_AT_ORIGIN` es la composición estática D11 y excluye íntegros ciclos previos. Cambiar una ventana de display nunca resella B ni convierte implícitamente HISTORY_START a flat.

`InputManifest` fija cada `{history_ref, revision_no, revision_digest, artifact_digest}`, selection/composition revision y digest si aplica, temporal metadata revision/digest, source cuts, cost/risk evidence policies, perfil/config/algoritmo, calendar y metric policy, ventanas y conocimiento. Historia N y N+1 son inputs distintos aunque compartan operaciones. Nada resuelve head/latest dentro de Compute. `generation_ref = D("lab-analysis-generation.v1", manifest + spec + result_digest)` usando receta wire de C; no incluye worker ID, timestamps de polling ni duración del cálculo.

`CurveResult = {generation_ref, spec, manifest, economy_status, reasons[], unit, currency?, origin_value, points[], operation_contributions[], coverage, exposure_state, exhausted_at?, first_unsized_operation_ref?, result_digest}`. Punto `{seq, economic_at, batch_ref, order_basis, contributors[], delta:Rat, value:Rat, peak:Rat, drawdown:Rat}`; contributor enlaza operation_ref/movement_ref o summary y revisión exacta. `operation_contributions` conserva Q_i, B_i, apertura, neto evaluado y suma de deltas del perfil; sirve para terminal metrics y auditoría, no es fuente económica nueva. `Rat={numerator,denominator}` como strings enteros canónicos, denominador positivo y fracción reducida; se persiste también display HE12, nunca usado para sumar, dimensionar o score.

Estados económicos: `READY|INSUFFICIENT_DATA|NOT_COMPARABLE|CAPITAL_EXHAUSTED`; cálculo `PENDING|RUNNING|PUBLISHED|OBSOLETE|FAILED_RETRYABLE|FAILED_PERMANENT`; exposición `FLAT|OPEN|UNKNOWN` independiente. Snapshot vacío con coverage completa permite origen/plano y contadores cero observados, pero desempeño sin operaciones devuelve métricas `NO_OBSERVATIONS`; no crea ganancia ni elegibilidad. Un OPEN con realizaciones completas conocidas puede tener curva realizada READY + `OPEN_EXPOSURE_UNMARKED`; READY nunca significa equity total conocido.

### 3. Economía y orden causal total

Las reglas acreditadas de Q_i, costes, monedas, grano y selección son las de C §4–§8. `d_ij` es contribución neta firmada conocida en economic_at; para movimientos suma realized gross y costes una sola vez, para CLOSED_SUMMARY usa su neto una sola vez al cierre. Q_i>0 es presupuesto de TODO el ciclo sellado antes/causalmente previo a primera exposición, con método/política/evidencia y moneda. FIRST_ENTRY_RISK/TICKET_INITIAL_RISK, pérdida observada, SL final y configuración actual no acreditan Q_i. Adds y cierres parciales no cambian Q_i ni B_i; una corrección fuente nueva se evalúa exclusivamente en otra HistoryRevision.

Algoritmo único de timeline, previo a todos los perfiles:

1. Resolver selección y crosswalk exactos de C; un solo grano por operación. Incluir ciclos según apertura del segmento; carry-out conserva su historia/cohorte y movimientos posteriores hasta el corte. Sin continuidad acreditada => estado insuficiente, nunca concatenar primera historia o duplicar summary+movements.
2. Aplicar el modo de conocimiento: revisión exacta retrospectiva, o snapshot/vintage y known_at/received_at acreditados para AS_KNOWN_IN_ECHO. Filtrar hechos económicos posteriores a as_of; un correction conocido hoy no se backdatea como conocimiento antiguo. No usar N+1 recortada para fabricar N histórica.
3. Crear eventos OPEN, MOVEMENT y SUMMARY con instantes PROVEN UTC. OPEN define primera exposición; sello Q_i es anterior y no es PnL. Ordenar timestamps económicos crecientes. Validar movimientos no anteriores a apertura y eventos/certificados contradictorios antes de calcular; falta de tiempo acreditado devuelve insuficiencia, no medianoche inventada.
4. Dentro de UN timestamp, usar secuencia sólo cuando la evidencia establezca un orden causal TOTAL de TODOS los eventos que pueden afectar saldo/presupuestos de ese timestamp. Un stream común de owner con seq y vínculo explícito al OPEN sirve; owner seq de cuentas distintas no compara. Causalidad inversa al timestamp o ciclo en evidencia => `CAUSAL_ORDER_CONFLICT`; nunca forzar orden por ID.
5. Con total probado, procesar cada evento en esa secuencia: OPEN sella B con saldo anterior a ESE evento; coste de su propio fill viene después del sello. Movimientos intermedios conocidos antes de otra apertura sí afectan su B. Cada estado de saldo es un punto económico válido, incluso si comparte timestamp.
6. Sin total probado, tratar TODO ese timestamp como un batch atómico: sellar todas sus aperturas sobre C(t−), aplicar luego la suma de movimientos/summaries del batch y emitir un único punto para DD. Las sumas por operación se conservan. Ni IDs ni el orden del JSON ni secuencia parcial dentro de un owner crean capital disponible dentro del batch. Una apertura y su comisión simultáneas reciben presupuesto antes de esa comisión. `batch_ref` deriva del timestamp+set de eventos; contributors se ordenan lexicográficamente sólo para serialización.

Esta regla produce un orden total de unidades económicas evaluables `(economic_at, proven_total_seq)` o `(economic_at, atomic_batch)`. No afirma cuál ocurrió primero dentro de un empate desconocido. DD tampoco usa una trayectoria arbitraria por IDs: movimientos −100/+100 simultáneos sin orden producen delta batch=0, y se declara resolución `TIMESTAMP_BATCH` al comparar precisión con datos secuenciados. Intercambiar IDs no cambia tamaños, balance ni DD.

| Perfil | Inicialización y contribución exacta |
|---|---|
| `recorded_money.v1` | P(0)=0; P(t)=Σd_ij por moneda probada. Ni depósitos/retiros/reset ni un 10k ficticio. No es balance/equity de cuenta |
| `r_net_cumulative.v1` | R(0)=0; Δ_ij=d_ij/Q_i. Q_i fijo por ciclo; suma R en tiempo económico, incluidos costes y parciales OPEN |
| `normalized_10k_open_balance.v1` | C(0)=C0; en OPEN i, B_i=r×C_preopen; Δ_ij=B_i×d_ij/Q_i; C(t)=C0+ΣΔ. B no se retira ni reserva; es sólo escala analítica |
| `normalized_10k_initial_balance.v1` | C(0)=C0; B_i=r×C0 en cada OPEN; Δ_ij=B_i×d_ij/Q_i. Misma causalidad y política de agotamiento, sin reinversión |

Operaciones concurrentes pueden presupuestarse cada una al 1% sin cap agregado. Este análisis no simula margen, colateral, admisión ni límites prop y no cambia decisiones MM. Una OPEN con neto parcial +40 y coste −2, Q100 y B100 da money38/R.38/C10038, sin trade terminal ni flotante cero.

NO_FX inicial: cada numerador y su Q_i deben compartir moneda probada; R y normalizados pueden agregar ciclos de distintos instrumentos/monedas después de obtener ese cociente dimensionalmente válido y con método de riesgo comparable. Recorded money devuelve series por moneda; no tiene total scalar para USD+EUR. Métricas money sólo por currency solicitada y un universo explícito; moneda desconocida conserva reason y no desaparece de coverage. No se deducen valores/pips por símbolo; conversión económica de fills pertenece al extractor owner/accounting. Extender FX exige dataset/rates/available_at pinneados como C, otra spec/config, nunca tasa actual o futura.

Costes omitidos no son cero. Con GROSS_ONLY/PARTIAL_NET se puede exponer evidencia/prefijo conocido, pero resultado neto completo, terminal metrics y ranking quedan insuficientes. Un summary neto observado inclusivo de costes conserva READY con breakdown ausente declarado; no exige fabricar desglose. Sin Q_i, money puede estar READY mientras R/normalizados quedan `QI_UNPROVEN` con operation_ref y affected_interval.

Agotamiento en ambos normalizados: al primer C≤0, guardar evento y saldo negativo exacto, sin clamp. Las operaciones que YA tienen B continúan aportando, aunque el saldo recupere signo positivo. Una nueva OPEN cuando C≤0 no recibe B; registrar first_unsized y omisión evaluativa explícita. Una vez existe operación no dimensionable, el resto completo no es certificable: no reactivar automáticamente nuevas aperturas en la cola porque su saldo posterior depende de economía omitida. Conservar el prefijo y flujos de operaciones ya presupuestadas como evidencia, `CAPITAL_EXHAUSTED` histórico y `INSUFFICIENT_DATA` para métricas completas/score. Nunca omitir silenciosamente esa operación o asignarle B=0.

### 4. Ventanas, métricas y comparabilidad

`MetricSpec = {metric_policy_id:"rank_economics.v1", formula_versions, from, to, economic_as_of, knowledge_mode, knowledge_cutoff?, drawdown_mode:WINDOW_LOCAL|CURVE_RUNNING, terminal_population:"WHOLE_CYCLE_TERMINAL_IN_WINDOW", calendar_ref, calendar_digest, sampling_policy_id}`. Intervalos `[from,to)`; cada movimiento en from entra y en to no. Para ranking as_of≥to y ventana cerrada; as_of puede mostrar evidencia abierta posterior en otra consulta sin cambiar este conjunto. El cálculo reproduce todo el warmup desde origin para los B y saldo inmediatamente anterior a from; no redimensiona por filtrar la UI.

Dos universos declarados en cada resultado: `FLOW_WINDOW` incluye TODOS los deltas realizados en ventana, incluso ciclos abiertos antes de from y ciclos todavía OPEN; `WHOLE_CYCLE_TERMINAL_IN_WINDOW` incluye cada ciclo cerrado completo cuyo closed_at está en ventana, aunque opened_at sea previo, y usa su resultado completo de por vida bajo el perfil seleccionado. Un parcial nunca es trade. Resumen/movimientos reconstruyen el mismo neto una vez. Reconciliación pendiente/economía terminal incompleta se cuenta entre faltantes y bloquea métrica terminal completa; no se reduce el denominador a los buenos. Reportar `n_terminal_expected`, `n_terminal_evaluable`, `n_open`, `n_carry_in_terminal`, `n_flow_cycles`, faltantes, cobertura y fechas junto a métrica para explicar la diferencia entre universos. PF/SQN no se calculan sobre la lista de movements ni sólo sobre el trozo de un ciclo que cae dentro de ventana.

Sea x_i el resultado COMPLETO del ciclo en unidad del perfil: neto money, neto/Q en R, o B_i×neto/Q en normalizados. Sea F=Σ deltas FLOW_WINDOW, y V(t) el valor del perfil. Para WINDOW_LOCAL, V_start=V(from−), peak inicial=V_start; para CURVE_RUNNING, peak inicial=max histórico antes de from. En money/R, V empieza en cero y DD es absoluto, sin porcentaje desde cero. En normalizados origen incluye C0. Evolucionar peak=max(peak,V), DD=peak−V≥0 después de cada evento o batch evaluable. Max DD toma máximo de esos DD; current DD es el último. Se preserva origen para que una primera pérdida produzca drawdown.

El calendario default `utc_day_365.v1` define bins `[00:00Z,00:00Z siguiente)` TODOS los días civiles UTC y A=365. Ref+digest pinnean límites, timezone, regla de anualización y versión; no inferir calendario de primer/último trade o instrumento. Sharpe usa sólo bins completos contenidos en ventana y completamente cubiertos; parcial de primer/último día se informa y no se anualiza como día entero. COMPLETE sin actividad da z=0, GAP/PARTIAL da insuficiencia de la serie completa; no eliminar días malos o sin datos. Para rankings ambos extremos son medianoche UTC y al menos 30 bins completos. Calendario de sesión alternativo es otra MetricSpec/cohort, con sus bins/A/evidencia explícitos; no mezclarlo con UTC365. Con multiinstrumento, exigir cobertura completa de toda la selección en cada bin; feriado de un instrumento no equivale a GAP si el calendario fuente acredita cero actividad.

Precisiones: sumas, medias, varianzas, PF, RetDD y z diarios son Rat exactos. SQN/Sharpe pueden ser irracionales: conservar expresión exacta `SignedSqrtRational={sign,radicand_num,radicand_den}` reducida (sign de mean; radicand=mean²×n/variance o mean²×A/variance). Además cada métrica DEFINED publica `calc_decimal` HE24 bajo `metric-calc-half-even-24.v1`, y `display_decimal` HE12 independiente. Calcular raíz/rounding con enteros big.Int y cotas racionales hasta probar el redondeo único a 24 decimales, incluida regla de empate; nunca float64 ni precisión big.Float fija no verificada. El único kernel compartido `weighted_combination_minmax.v1` de E recibe calc_decimal con esa policy, convertido UNA vez al borde mediante binary64 nearest-even finito validado; guarda el decimal original y bits recibidos. El kernel conserva la aritmética float64/orden de operaciones observados en Forge y su versión; display no entra al score. La prohibición de float64 en economía y cálculo de métricas no se extiende a ese kernel de ranking explícitamente versionado. No hay segundo motor decimal ni se alega paridad SQX de métricas económicas distintas. Exactos racionales también se cuantizan una sola vez al mismo contrato computacional de ranking. Cambiar precisión exige versión/policy y cohort nuevos.

`MetricValue = {id, formula_version, status:DEFINED|NO_OBSERVATIONS|INSUFFICIENT_DATA|UNDEFINED|NOT_APPLICABLE, exact_value?, calc_decimal?, display_decimal?, unit, population, n_expected, n_evaluable, n_bins, window, reasons[], generation_ref, metric_spec_digest}`. NULL es ausencia junto al estado; cero válido es DEFINED "0". Error técnico de cálculo se registra en job; no se presenta como dato faltante ni como score0. Métricas no implementadas no se anuncian en catálogo enabled; un consumidor que pida ID no implementado recibe error explícito.

`ComparabilityKey` fija perfil+versión/config efectiva, precision y order-resolution policy, unidad/moneda cuando aplica, método semántico Q_i/política de acreditación, cost/net basis, terminal_population, flow policy, metric_policy/formula versions, drawdown_mode, ventana/as_of/knowledge, calendar digest, sampling policy, origen/reset y continuidad/MM declarado. Mismo risk method debe certificar la misma semántica de presupuesto de ciclo, no necesariamente un mismo ID de decisión; conservar evidence individual. Diferencias de moneda fuente tras R válido se muestran, sin volverlas USD. Recorded money requiere moneda común y comparación explícitamente observada bajo MM homogéneo; normalizar resultados no acredita misma gestión fuente ni costes equivalentes. Precisión summary al cierre vs movimientos intradiarios se declara: no certificar mismo DD/Sharpe cuando su resolución económica es distinta. Historia continua con CONTEXT_DISCONTINUITY o coverage GAP bloquea cohort homogénea; perfiles alternativos se comparan en cohort distinta. No se afirma equivalencia estadística por tener igual valor.

Contrato D/E definitivo: ambos presets `edge_duo.v1` y `forge_quality_four.v1` usan `rank_economics.v1`, WINDOW_LOCAL, WHOLE_CYCLE_TERMINAL_IN_WINDOW, `ranking_sample_30x30.v1` (≥30 ciclos terminales completos y ≥30 bins diarios completos), UTC365/rf0 y default normalized open C0=10000/r=.01/NO_FX. Edge exige sus dos métricas DEFINED, Forge sus cuatro; un factor faltante no redistribuye pesos. Los mínimos son eligibility, no alteran fórmulas ni impiden exponer SQN/Sharpe definidos con n≥2; no representan significancia ni certificación de estrategia. Cambiar curva visible no cambia el ranking snapshot ni selecciona otro perfil sin nueva petición explícita. Los pesos/minmax/ties y evidencia Forge pertenecen a E.

### 5. Invalidación, dependencias y worker durable

Persistencia TARGET mínima en `lab.*`: `analysis_targets` (PK target_ref scoped, target_kind, desired_seq int64 monotónico, desired_manifest_digest, desired_spec_digest, current_generation_ref nullable, lease_owner?, lease_until?, fencing_token int64 monotónico, attempts, next_attempt_at, last_error), `analysis_generations` (generation_ref, target_ref, input_manifest, spec, status, result_digest, input/outcome counts), `curve_points`, `operation_contributions`, `metric_values`, `analysis_dependencies` (target_ref, dependency_kind/ref, revision/digest), `analysis_attempts` (target_ref, desired_seq, fencing_token, started/ended/status/error). Las generaciones/outputs publicados son inmutables; state vigente es un pointer, no UPDATE de sus inputs. Error/lease no entra al digest económico.

Ingestión/corrección de C inserta outbox dirty y mueve head en la misma transacción. Servicio de selección/composición/config hace lo mismo con su revisión y dependientes. Un relay idempotente procesa outbox local PG y actualiza target desired_seq/manifest + marca delivery en una transacción; no existe ventana donde confirmar delivery antes de encolar. Unique `(outbox_event_ref,target_ref,spec_digest)` evita duplicar un mismo cambio. Un reconciliador periódico de bajo coste compara desired/head/spec digests y reencola deltas perdidos; no es scheduler de portfolios. Ingestión devuelta ACCEPTED significa durable outbox, no curva calculada.

`analysis_dependencies` registra historias/revisiones, selección, temporal metadata, composición, catálogo/spec/config/metric/calendar y cohort membership de E. Cambio de historia sólo invalida sus targets y dependientes transitivos; no recalcula todas las estrategias. Cambio de selección invalida curva seleccionada, métricas, composición que la usa y ranking cohort correspondiente. Cambiar un punto histórico puede alterar TODOS los B posteriores de open_balance; I1 reconstruye toda la curva afectada desde origin y sus métricas, sin parche de último punto ni incremental especulativo. Cada perfil publica READY o sus razones específicas; dependencia no evaluable no se cambia por otra silenciosamente.

Jobs current son coalescidos por target: desired_seq más reciente gana, sin calcular obligatoriamente cada N intermedia. Petición PINNED de N crea target separado por manifest digest y se reproduce aunque head sea N+k; nunca se promociona como current. Registry/metric/config nuevos crean otra spec y desired target, preservando generaciones antiguas.

Protocolo único de locks entre writers y publisher: primero advisory transaction locks de todos los recursos mutables de entrada, ordenados byte a byte por `(namespace, resource_kind, resource_ref)` y con la misma receta compartida; luego target rows ordenadas por target_ref. Writers de historia/selección/composición conservan esos locks hasta actualizar head, insertar outbox y commit. Publisher los conserva hasta verificar/mover pointer. Hash collision de advisory lock sólo serializa, no sustituye comparación de refs/digests. Ninguna ruta toma target y luego intenta adquirir recursos de entrada. Claim/heartbeat usan sólo target row y terminan antes de leer inputs; jamás calculan bajo lock.

Secuencia del worker:

1. Claim corto con `FOR UPDATE SKIP LOCKED` sobre target pendiente cuyo next_attempt_at≤DB clock y lease ausente/vencido. Copiar desired_seq/spec/manifest; incrementar fencing_token; asignar lease_owner UUID del intento y lease_until=DB now+60s; registrar attempt y commit. SKIP LOCKED sólo para cola, no lectura de datos económicos.
2. Leer input manifest exacto con RR de corta duración; verificar artifacts/digests antes de soltar snapshot. Refs de revisión inmutables permiten streaming/spool de trabajo fuera de DB sin perder coherencia. Si desired_seq ya cambió, terminar OBSOLETE y liberar lease propio condicionalmente; no calcular input viejo current.
3. Calcular fuera de transacciones largas; context cancel y heartbeat cada 20s. Renovación `WHERE target_ref AND lease_owner AND fencing_token AND lease_until>DB now`; pérdida de una condición cancela publicación. Expirado no se revive por el mismo token: se reclama con nuevo token. Un proceso lento no puede conservar autoridad porque todavía siga vivo.
4. Preparar generación candidata invisible, validar counts, conservation y digests. Staging está aislado por intento; no hay lecturas Hasura/directas de parciales. Resultado económico insuficiente es outcome válido a publicar, no retry infinito.
5. Publicar en transacción corta: adquirir recursos/targets con orden anterior; comprobar TODOS los heads de historia/selección/composición/metadata, spec/catalog/calendar/metric digests, desired_seq y lease/token propietario aún no vencido. Insertar header, puntos, contribuciones, métricas, coverage y referencias/estado; cambiar current_generation_ref y finalizar attempt con CAS en la misma transacción. Si cambia cualquier entrada o lease, rollback de promoción, outcome OBSOLETE/LEASE_LOST, conservar/enqueue desired vigente. No vale SELECT de validación y luego UPDATE sin lock común.
6. Un commit cuyo ACK se pierde se recupera leyendo generación/attempt por target+seq+token/result_digest; no repetir publicación a ciegas. Reintento idéntico usa mismo generation_ref y converge; resultados distintos para mismo manifest/spec => `NONDETERMINISTIC_RESULT`, fallo permanente visible y sin sobrescribir el primero.

Retries recuperables DB/artifact/red: máximo 5 intentos consecutivos por desired_seq, backoff 1/2/4/8/16s sin random (lease vencido puede recuperarse). Publicación transaccional o incertidumbre se inspeccionan primero. Agotado => FAILED_RETRYABLE con error/next_action visible y manual retry mismo manifest sin perder puntero previo; nueva revisión/config reinicia contador para su desired_seq. Shape/digest inválido, algoritmo desconocido o invariant interno => FAILED_PERMANENT; el error indica campo/evidencia, no se omite la operación. Readiness operacional de B/A no depende de este estado analítico.

Worker I1 default acotado: 2 cálculos concurrentes/proceso, 1 intento activo por target, claim batch≤2; no lanzar un job por símbolo ni historial entero por estrategia indiscriminadamente. Input spool respeta límites de C (hasta 250k operaciones/1M movimientos por historia y ≤8 historias por request); esos caps no certifican RAM/latencia. Medir capacidad real en Shot 2/3 antes de aumentar concurrencia. Queue age, dirty/desired lag, lease lost, obsolete, retry, duration, input counts, output counts y current/head gap son métricas operativas sin datos/secretos del payload. No Kafka/Temporal nuevo para esta cola PG.

### 6. Publicación dependiente, composición y read models

Un resultado de historia puede publicar sus cuatro perfiles en UNA generación analítica por vector de inputs, con estado separado por perfil; esto evita un current de un perfil nuevo presentado como si sus hermanos hubieran terminado. Las configs personalizadas tienen su target y publicación independientes. El bundle default no espera que todos sean READY: N+1 puede publicar money READY y R/10k INSUFFICIENT_DATA de forma terminal/coherente. Si un perfil falla técnicamente, el bundle no se promociona y conserva el anterior con error; no deja una familia a medias.

Ranking/cohort de E fija lista completa de miembros elegibles/excluidos y cada generation_ref+metric_spec_digest. Publicar nuevos resultados de un miembro invalida el cohort deseado, pero no cambia parcialmente scores/normalizadores. El publisher de cohort aplica el mismo protocolo a membership/selection/targets de TODOS sus miembros y publica cabecera, métricas de input, rangos min/max, scores/ranks/ties/reasons y pointer cohort en una sola transacción. Si un miembro cambia durante cálculo, candidato OBSOLETE y se recalcula cohorte; no mezclar métricas N y N+1 dentro de un rank snapshot ni recalcular sólo su score con viejos extremos. Inputs históricos pinneados siguen consultables sin ser current.

D11 usa C §8: Σw≤1, cash remanente, capital separado C0_j=w_jC0, inicio FLAT con ciclos opened_at≥composition_start_at, presupuesto causal propio por miembro y ningún préstamo/rebalanceo. C_total=cash+ΣC_j. Peso cero no requiere datos; peso positivo con GAP/insuficiencia agota el resultado compuesto completo, sin renormalizar pesos ni volverlo cash. Recalcular desde inicio; sólo reescalar componente si manifest prueba homogeneidad exacta y mismos ciclos/origen/policy, sin redondeos intermedios. Perfil recorded_money no se reescala a nuevo capital, R no se suma como saldo. Composición fija cada revisión de input y su propia spec/pesos, no reescribe snapshot previo al actualizar head.

Read model por solicitud devuelve `{target_ref, head_revision_vector, desired_seq, displayed_revision_vector, generation_ref, metric_spec_digest, economic_status, calculation_status, is_stale, reasons, points_page, metrics, counts, selection_revision, profile_spec}`. Mientras head=N+1 y displayed=N, banner pendiente y TODOS los datos económicos, conteos, operaciones y movements explicativos son N. No tomar count del head para explicar PF/curva antiguos. La pantalla puede mostrar head más reciente sólo como metadata identificada aparte. Cuando publica N+1, el pointer cambia y nueva solicitud adopta el bundle completo.

Pagination cursor firmado/scoped contiene namespace, target_ref, generation_ref, revision vector digest, query/filter/sort digest y última clave estable; operaciones ordenan por `(opened_at,operation_ref)` y movimientos `(economic_at,batch_ref,seq,movement_ref)` de esa generación, sin OFFSET mezclado con head. Cambiar sort/filtro exige cursor nuevo; cursor de N sigue leyendo N después de publicación N+1. Sin generación visible inicial se devuelve PENDING y reasons sin métricas fabricadas. Referencia no autorizada=>404 scoped; cursor inválido=>400; cursor de otra consulta/generación=>409 `CURSOR_CONTEXT_CONFLICT`; artifact temporalmente ausente=>503 y error íntegro, nunca fallback head. C I1 conserva inputs/outputs referenciados sin GC automático.

Hasura expone sólo vistas/publicaciones completas con filtros namespace/roles de [[F — SQL Hasura UI Integration]]; mutations de ingestión/selección/composición/retry pertenecen a servicios Echo autorizados. La fuente runtime/Operation/journal continúa siendo de su owner; datos analíticos nunca autorizan Signal/orden ni sobrescriben journal.
