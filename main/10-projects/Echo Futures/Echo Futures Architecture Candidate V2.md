## 1. Architectural outcome

Echo Futures V1 is one deterministic domain and runtime path reused across LIVE, EXACT_REPLAY and BACKTEST:

```text
Market sources
  -> echo/market_stream              key stream_id
  -> echo/market_analytics           key stream_id
  -> echo/strategy_engine            key strategy_id
  -> Signal
  -> echo/signal_fanout              key strategy_id
  -> SignalDelivery
  -> echo/operation                  key account_id:account_strategy_id
       -> MoneyManagement plugin
       -> echo/provider_rules        key account_id
       -> provider authorization
       -> M1 command publication
  -> Futures Bridge sibling
       -> ExecutionAdapter
       -> M2 physical side effect
  -> normalized execution observations
  -> echo/operation / Position-Reconciliation
```

The design deliberately avoids a portfolio engine, workflow/saga layer, global event sequencer, provider-specific MoneyManagement hierarchy, global coordinator, event-sourcing rewrite or a generic bridge framework.

The scale target remains **100–200 accounts without architectural redesign**. Market ingestion, bars, indicators and Strategy evaluation are shared by stream/Strategy; account multiplication begins only after Signal fan-out.

## 2. Domain model

### 2.1 Strategy

A Strategy owns technical market interpretation only. It consumes canonical market/context inputs and produces immutable `Signal` objects carrying technical intent, direction, instrument and technical details.

Strategy does not own:

- account balances or account-day economics;
- provider policy;
- position sizing;
- money loss/profit objectives;
- Orders/Fills/physical Position;
- GerardMM profit targets.

For S1 and S2, Strategy may provide a **technical_stop**. Neither Strategy provides a monetary/fixed profit target.

### 2.2 Signal

Canonical Strategy output:

```text
Signal {
  signal_id
  strategy_id
  strategy_cycle_seq
  intent                  OPEN | REDUCE | CLOSE | CLOSE_ALL
  instrument_id
  direction?
  details                 technical Strategy-specific payload
  created_at
  valid_until
  provenance {
    strategy_eval_seq
    signal_seq
    trigger_identity
    run_mode
    run_id
    source
  }
}
```

`signal_id` is deterministic from stable run/evaluation identity. `strategy_cycle_seq` identifies the technical cycle; it is a scalar, not a new aggregate.

### 2.3 AccountStrategy

`AccountStrategy = Account + Strategy + MoneyManagement + enabled/config`.

It is the binding that receives immutable Signals after fan-out. Transport/provider fields remain account-owned through `ProviderAccountBinding`; they do not move into AccountStrategy.

### 2.4 MoneyManagement

MoneyManagement is an economic decision plugin invoked inside the `echo/operation` state owner. Its durable mutable state is the namespaced `mm_state` stored with the Operation.

MoneyManagement owns:

- exact quantity decisions;
- monetary risk budget;
- bounded adds;
- protective-stop policy;
- account-day profit objective behavior;
- termination decisions generated by its economic policy.

MoneyManagement does not enforce provider policy. It receives the **complete ProviderRuleSet read-only** as context where account-specific economic behavior needs it, while `echo/provider_rules(account_id)` remains the final external policy authority.

### 2.5 Operation

Operation is the aggregate root of one materialized AccountStrategy execution lifecycle.

Core invariants:

- at most one non-terminal Operation per `(execution_account_id, account_strategy_id)`;
- direction is sealed from the accepted OPEN Signal and immutable;
- `contract_id` and required Contract specs are pinned at materialization;
- logical exposure is derived only from immutable Fill truth;
- no clamp, synthetic Fill or Position-based Operation attribution;
- terminality requires simultaneously:
  `logical_exposure == 0`,
  zero live Orders,
  and a recorded termination intent;
- ForceClose is an intent, never instant terminality;
- reversal is old Operation termination plus a later technical cycle.

### 2.6 Order

Order is an entity inside Operation. `order_id == client_order_id` is stable across delivery/restart and is the M2 correlation identity.

Each Order owns exact requested quantity and the D4-A2 executable envelope value:

```text
q_exec_max
= maximum remaining quantity that can still physically execute
  under the latest venue-authoritative finality evidence
```

Any outstanding executable Order participates in safety calculations according to its signed physical effect, not merely its semantic role label.

### 2.7 Fill

Fill is an immutable venue fact. Canonical dedup uses a native stable execution identity scoped with account, normally:

```text
(execution_account_id, provider_execution_id)
```

Price/time/qty hashes, local sequences and arrival order are not acceptable substitutes for restart-safe physical identity.

### 2.8 Position

Position is physical venue observation scoped by:

```text
(execution_account_id, contract_id)
```

It is net physical truth and is never used to infer which logical Operation owns exposure. Unknown/manual activity remains physical observation plus reconciliation debt.

### 2.9 Instrument and Contract

`Instrument` is Echo's canonical economic identity, for example NQ. It owns canonical `exchange`, `product_group`, quote currency and `calendar_ref`.

`Contract` is the tradable expiry-specific instrument, for example NQZ6, with `tick_size`, `point_value`, derived `tick_value`, and quantity rules.

Strategy knows Instrument. Operation resolves and pins exactly one Contract. Rollover is owner-controlled, hot and prospective; it never retargets a live Operation.

### 2.10 TradingSession / Calendar

`ExchangeCalendar` is owner-managed, DST-aware through named IANA timezones and is resolved by `calendar_id`. Session identity is:

```text
(calendar_id, session_date)
```

`NamedTradingWindow` is pure config. Exchange availability and named windows are separate and composed explicitly.

`account_day` is a different contractual clock owned by account/provider configuration. It is never substituted by exchange session date.

### 2.11 Provider / Program / RuleSet

The provider model is:

```text
Provider
  -> ProviderProgram
      -> optional provider-local phase
      -> ProviderRuleSet
Account
  -> ProviderAccountBinding
```

ProviderRuleSet is typed data, not a DSL. The effective RuleSet remains **complete** when exposed read-only to MoneyManagement/account-specific context.

`echo/provider_rules(account_id)` owns authoritative account-wide admission, reservations, provider risk state, entitlement state and safety triggers. It does not become a second MoneyManagement.

| State / decision | Owner | Key |
|---|---|---|
| logical market stream, canonical ordering, authority epoch/readiness | `echo/market_stream` | `stream_id` |
| forming/closed bars, shared analytical market state | `echo/market_analytics` | `stream_id` |
| technical cycle, Strategy indicators/readiness/config | `echo/strategy_engine` | `strategy_id` |
| Signal target-set linearization + delivery dedup | `echo/signal_fanout` | `strategy_id` |

No other mutable V1 state owner is introduced.

## 4. Market identity, ordering and deterministic observation

### 4.1 Stream identity

```text
stream_id = (instrument_id, contract_id)
```

The stream is economic and stable through market-source switches. Market source/binding is metadata expressed through serving authority and `authority_epoch`.

A source switch does not roll the Contract. Rollover creates demand for another logical Contract stream prospectively.

### 4.2 Canonical event identity versus order

D4-A1 freezes:

```text
canonical_event_id != stream_seq
```

- `canonical_event_id` answers **which canonical fact is this?**
- `stream_seq` answers **where is this fact in the durable canonical order for this stream?**
- source-native identity/position answers what the upstream source actually identifies;
- `authority_epoch` identifies the serving authority epoch.

Every decision-capable input must enter a durable unique order per `stream_id` before canonical downstream mutation. No global market sequencer exists.

Redelivery with the same stream sequence, canonical identity and digest is a no-op. The same `stream_seq` resolving to a different canonical fact is a fail-visible identity conflict, never silently accepted.

### 4.3 Bars and late data

Bars are shared projections, not decision observations. They are built session-aware, timer-closed, with no synthetic empty bars and no bucket crossing exchange boundaries.

A late market correction may update the market projection. It **must not mutate a past Strategy/MM decision** that consumed the earlier version.

## 5. MarketContext and EXACT_REPLAY

A decision receives a read-only `MarketContext`. In LIVE it may query shared read models. The decision records only the exact decision-critical reads it actually consumed:

```text
context_reads[] {
  read_ordinal
  logical_read_key
  observed_version
  value_ref? | inline_value?
  content_digest
}
```

Within one decision, repeated logical reads are memoized to the same observed version.

EXACT_REPLAY reconstructs the decision from the recorded ordered input plus its `context_reads[]`; it never substitutes today's/latest shared state. Missing, extra or incompatible context is a replay failure.

Cross-stream decisions record each consumed read separately. V1 does not require an atomic multi-stream snapshot.

Always-on recording applies to the streams actually selected/demanded by a run. ReplayAnchor is captured from run start for those requirements.

Explicitly absent:

- `DecisionObservation`;
- `BarObservation`;
- giant state snapshots;
- global sequencer;
- global event sourcing.

## 6. Strategy runtime and fan-out

A Strategy evaluation is sequential inside `echo/strategy_engine(strategy_id)`:

```text
admitted trigger
  -> deterministic evaluation
  -> technical state mutation
  -> 0..N ordered Signals
  -> transactional Signal egress
```

Strategy trigger requirements are declarative and minimal: bar closes, optional market-event class, window/session transitions and timers. No Strategy DSL or plugin orchestration framework is introduced.

The fan-out evaluates the AccountStrategy target set once per immutable Signal and delivers it account-by-account. It does not recompute Strategy indicators or technical logic per account.

The only account-specific economic computation after fan-out is Operation/MM/provider/execution logic.

## 7. Concrete Strategy V1

### 7.1 S1 — NY Opening Range Breakout 30m

Instrument: NQ.

Inputs:

- canonical 5m bars;
- canonical TRADE events;
- `NY_OPEN` authority resolving 09:30–10:00 America/New_York intersected with exchange availability;
- required configured `premarket_window_id`.

The opening range is exactly the canonical closed 5m bars in NY_OPEN. A missing/unprovable range fails closed for that day.

Breakout is a strict crossing on canonical TRADE after the opening range closes.

At OPEN decision time:

```text
LONG technical_stop =
  lowest closed-bar low from configured premarket start
  through the previous closed 5m bar

SHORT technical_stop =
  highest closed-bar high over the same interval
```

The forming 5m candle is excluded. The premarket start hour is not hardcoded; absence/invalid config fails closed.

S1 has no profit target. Its technical lifecycle uses OPEN and CLOSE_ALL. Stop hit, re-entry into the opening range and day/window transition follow the frozen S1 state machine. Re-arm requires the frozen closed-bar condition; no discretionary interpretation exists.

### 7.2 S2 — H4 Trend / 5m Bollinger Pullback

Instrument: NQ.

S2 combines H4 trend context with 5m Bollinger pullback setup using frozen closed-bar semantics. It emits a technical stop with the OPEN Signal.

The Bollinger basis is **not** a profit target and is not carried as a GerardMM target. A return to the basis is a Strategy technical lifecycle condition that emits `CLOSE_ALL`. Trend invalidation is likewise technical close behavior.

S2 and S1 share the same Strategy runtime, Signal identity, fan-out and replay boundaries.

## 8. Account admission and pending OPEN

Stage-1 OPEN admission is asynchronous but deliberately not modeled as a generic workflow.

Inside `echo/operation(account:account_strategy)` there may be one nullable owner-local state:

```text
pending_admission? {
  request_id
  opening_signal_id
  strategy_cycle_seq
  opening_signal_delivery
}
```

It is not an Operation, aggregate, entity, service or saga.

Rules:

- OPEN establishes pending admission before sending the authoritative account-scoped request.
- only the still-active matching ALLOW may continue materialization;
- CLOSE/CLOSE_ALL for that cycle invalidates pending admission;
- OPEN(k+1) supersedes the older pending cycle;
- late ALLOW/DENY for an inactive request is idempotent stale input;
- no arbitrary queue/backlog of pending cycles exists.

An admitted OPEN materializes the Operation only after all materialization guards pass, including valid Signal, enabled binding, Contract/calendar resolution and provider authority.

## 9. Executable exposure and capacity safety

D4-A2 replaces role-based shortcuts with executable signed quantity.

### 9.1 Local Operation safety

For every live Order, `q_exec_max` describes what can still execute.

For a LONG Operation with signed fill exposure `e_o > 0`, all outstanding sell-side executable claims must jointly satisfy the non-inversion envelope. SHORT is symmetric.

Two concurrent reductions cannot both claim the same reducible exposure. EXIT and ForceClose use the same local claim mechanism; ForceClose cannot blindly submit another full close while a reducing Order may still execute.

Cancel request alone does not free the claim. Venue-authoritative finality or an acknowledged quantity reduction is required.

ENTRY/ADD is blocked once termination intent is active.

### 9.2 Account-wide provider capacity

Where a configured shared provider cap is affected by executable quantity, provider reservations model the **reachable physical envelope**, not semantic labels.

Supported V1 families remain typed:

- `GROSS`;
- `NET_ABS`;
- `GROUP_WEIGHTED`.

Reservations account for any Order that can affect that cap, including reductions/exits when netting means they can enlarge the worst-case reachable absolute exposure under another valid execution ordering.

Fills transfer reserved executable quantity into firm exposure; they do not optimistically widen the safety envelope.

Modify increase reserves its delta before authorization. Modify decrease only releases after authoritative acknowledgement. Replace counts old and new legs while both can still execute.

There is no silent resize. An exact denied quantity is denied; caller may make a later explicit decision.

Position observations never reattribute Operation exposure.

## 10. Provider authorization before command publication

Every exact provider grant that has not yet crossed Core egress must traverse the authoritative final revalidation:

```text
ReservationRevalidate
  -> echo/provider_rules(account_id)
```

No local “rule epoch unchanged, skip revalidation” fast path exists.

A successful revalidation marks the exact existing reservation:

```text
egress_authorized
```

with current authority provenance. This is a one-shot provider authorization point for that exact grant.

The following are distinct and must never be named or reasoned about as one event:

```text
provider authorization point
!= M1 Core command visibility
!= M2 physical venue point-of-no-return
```

`egress_authorized` is not called `egress_committed`.

If revalidation fails, the command never crosses M1; the durable Order/provider-decision state converges locally and any local executable claim/reservation is released according to the invalidation contract.

## 11. GerardMM V1

### 11.1 Boundary

```text
Strategy
  -> technical intent + technical_stop

GerardMM
  -> money/risk/sizing/adds/protection/account-day profit objective

provider_rules
  -> final external account-wide policy enforcement
```

### 11.2 Owner economic plan

Evaluation:

```text
business day 1: SL = 2000 USD, TP = 1500 USD
business day 2: SL = 2000 USD, TP = 1500 USD
```

A day without configured economics fails closed for new risk.

Funded schema has:

```text
FUNDED_INITIAL
FUNDED_STEADY
```

but numerical values are required configuration. No default amounts are invented.

### 11.3 Account-day authority

Both Owner SL and TP are account-day scoped and consume:

```text
account_day_current_pnl_money
```

This is the authoritative current realized + unrealized PnL for the whole account day as supplied by Account state. GerardMM does not reconstruct a portfolio or attribute other Operations itself.

```text
remaining_profit_objective_money =
  max(0, configured_TP - account_day_current_pnl_money)

owner_remaining_loss_budget_money =
  min(
    configured_SL,
    max(0, configured_SL + account_day_current_pnl_money)
  )
```

The effective loss budget is further constrained by applicable ProviderRuleSet hard monetary headroom.

If required account-day economics are absent, stale or not deterministically convertible to the needed currency, new risk fails closed. Exit/safety actions are not reclassified as new risk merely because new-risk economic input is unavailable.

### 11.4 Dynamic profit exit

No fixed Strategy target price exists.

For a live Operation, GerardMM derives an **implicit current target mark** from:

- current remaining account-day monetary objective;
- current Operation quantity;
- current exit-side mark;
- point value.

The mark is derived and never persisted as authority. When account-wide PnL already reaches the objective, GerardMM blocks new risk and enters the profit termination path before add logic.

### 11.5 Bounded hardscalping

V1 preserves:

- one mutually exclusive branch per Operation: adverse or favorable;
- bounded configured add counts;
- exact quantities;
- partial Fill truth;
- no top-up after a partial add Fill;
- provider deny/invalid grant locks further new-risk scaling for that branch/Operation as specified;
- no inter-Operation martingale;
- no unlimited progression.

Research thresholds are seeds for research/test only. LIVE/DEMO requires explicit config.

Protective stop never loosens. Candidate quantity changes are evaluated against the resulting economics and exact executable/provider constraints before authorization.

## 12. Provider safety and ForceClose

Provider rules may independently trigger safety intents when their typed rule explicitly requires it.

Provider ForceClose:

1. records a `SAFETY_PLANE` termination intent in every affected live Operation;
2. invalidates new-risk decisions;
3. cancels/reduces outstanding executable exposure using the same q_exec/local-claim and provider-capacity rules;
4. waits for venue finality and Fill truth;
5. reaches `TERMINAL(SAFETY_FLATTEN)` only when the normal terminal guards are true.

Entitlement revocation is not automatically a ForceClose rule. It may suspend automated emission and require operator action according to the provider contract.

No generic liquidation override exists.

## 13. Execution architecture

### 13.1 Futures Bridge sibling

Futures execution lives in a sibling process that reuses existing Echo SDK/patterns without deforming the MT Bridge and without extracting a generic bridge framework.

Bridge responsibilities are limited to:

- per-account/binding command consumption;
- adapter/session lifecycle;
- M2 durable journal;
- physical reconciliation;
- normalized physical observations;
- health/readiness/telemetry.

It has no Strategy, MM, provider business rules, sizing or rollover logic.

### 13.2 M1

```text
StateFun state + transactional Kafka command egress
= M1 EXACTLY_ONCE state-to-command boundary
```

M1 means no physical command becomes visible from Core without corresponding committed Core state. It does not guarantee an external side effect occurs once.

### 13.3 M2

Before the first physical point-of-no-return the side-effect owner durably records the full intent. Required journal states remain conceptually:

```text
PREPARED
SUBMITTING
VENUE_BOUND
TERMINAL
AMBIGUOUS
```

Physical retry after possible side effect is forbidden unless native idempotency makes it safe with the same identity or authoritative reconciliation proves absence.

Unresolved outcome stays `AMBIGUOUS` and blocks new risk.

### 13.4 Readiness and reconnect

Socket connectivity is insufficient. New-risk readiness requires static eligibility plus live authenticated binding, event stream, reconciliation authority, fresh position state, exact submission capability and no unresolved M2 ambiguity.

Reconnect is recovery, never resubmit:

```text
authenticate
-> verify binding
-> restore subscriptions
-> load non-terminal journal
-> reconcile physical orders/actions
-> recover missing executions
-> obtain fresh Position
-> surface mismatches
-> only then reevaluate readiness
```

V1 has one active side-effect authority per physical account binding and no automatic cross-host takeover.

## 14. Configuration: hot versus pinned

Pinned with a live Operation:

- `contract_id` and required Contract economic specs;
- effective MoneyManagement config for the Operation;
- physical binding for every already-submitted Order/action.

Hot/prospective:

- Instrument→Contract mapping for future materializations;
- provider RuleSet/binding authority for future decisions and safety reevaluation;
- account state;
- market authority/source;
- calendars/windows through ordered material transitions;
- Strategy config activates according to the Strategy-cycle rules.

No hot update rewrites past decisions, a live Operation's pinned Contract, or already-issued physical binding.

## 15. Durability and projections

Recovery authority:

- StateFun checkpointed keyed state + Kafka replay for Core runtime;
- transactional fact/command egress at the required state boundaries;
- M2 journal in the physical side-effect owner durability domain;
- venue/history as physical truth.

PostgreSQL is a query/projection/config authority where explicitly defined, not Operation recovery authority and not M2 truth.

Fills remain append-only facts. No global event-store aggregate is introduced.

## 16. Failure semantics

Fail closed for new risk when correctness cannot be proven, including:

- required market/calendar/analytical readiness missing;
- Contract/identifier resolution missing;
- provider admission state unavailable/stale;
- exact provider revalidation invalid;
- account-day economic plan missing/stale;
- physical Position untrusted where provider cap correctness requires it;
- M2 ambiguity or insufficient adapter capability;
- entitlement UNKNOWN/FORBIDDEN;
- cold execution recovery without required checkpoint/physical evidence.

Fail-visible rather than silent repair for:

- canonical identity conflict;
- logical exposure invariant breach;
- Position mismatch/manual activity;
- late physical events;
- provider over-limit existing exposure after a hot cap change;
- inaccessible original transport for a live Order.

## 17. Scale model

The V1 topology is structurally:

```text
1 Strategy market evaluation
  -> 1 immutable Signal
  -> N AccountStrategy deliveries
  -> N account-local Operation/MM decisions
```

Market feed normalization, bar building, shared market state and Strategy indicators are not duplicated per account.

Legitimate account-linear work is confined to fan-out, MoneyManagement, provider/account reservations, command routing, physical session/reconciliation and projections.

A 100–200 account load therefore does not require architectural changes, though physical throughput/latency/journal/Kafka/session capacity must be measured and certified in D6.
