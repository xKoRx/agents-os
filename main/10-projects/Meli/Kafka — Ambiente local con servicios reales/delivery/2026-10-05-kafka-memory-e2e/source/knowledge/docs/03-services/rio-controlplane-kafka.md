# rio-controlplane-kafka

Snapshot canónico: `fury_rio-controlplane-kafka@f74e856ef3de881e2d504c6cb1ced573681c1058` (`master`). Las capacidades existentes en código no acreditan release, binding o ejecución E2E.

Guard candidato T23 en `eee5b909` ACK-ignora metadata wire obligatoria ausente antes del executor/claim; conserva deployment_group_id y cada Action component/environment nullable por compatibilidad. No reemplaza el enforcement master de esta página. La regresión de 804 tests es unit/mock integration; los cuerpos físicos quedan NOT_EXECUTED. [Campos, fuentes y límites](../08-governance/kafka-canonical-audit-2026-10-01.md#preparación-t23t26-y-límites-de-la-evidencia).

La [frontera upstream Kafka de Playmaker](../08-governance/kafka-canonical-audit-2026-10-01.md#revalidación-focal-del-nuevo-master-playmaker) se revalidó contra master `0c83575`. Deployment local Kafka ya es canónico allí; acciones/KVS/Service PEEK real del harness permanecen en checkpoint `1b4b8e1` y no acreditan ejecución completa.

## Rol

Administra topics Kafka con `PROVISION`, `UPDATE` y `DEPROVISION` por triggers asíncronos; ofrece peek como action y por HTTP. MSK y GCP tienen processors y contratos de parámetros distintos.

## Límites: qué hace y qué no hace

No hay REST directo de create/update/delete ni scheduler `@Scheduled` en este corte. La implementación GCP real usa `GcpKafkaAdminClientFactory`; el fallback no-op se registra sólo si falta una implementación. El CP no diagnostica la causa del lag ni define políticas de capacidad, mantenimiento o tuning. La ruta base Playmaker envía `aws-msk-topic`/`kafka-topic` a BigQueue y `gcp-kafka-topic` al catch-all `MATERIALIZER_REST`: aceptar el tipo GCP aquí no prueba ese journey upstream. Ver [routing](../05-contracts/component-routing.md).

## Persistencia y estado

KVS usa `deployment:<id>` para MSK, `gcp-deployment:<id>` para GCP y `action:<id>` para actions. El enum persistido es `IN_PROGRESS/COMPLETED/FAILED`; `PUBLISH_PENDING` es un `outcomeCode` dentro de `IN_PROGRESS`, no otro estado. El guard crea el registro, relee la versión asignada y hace updates CAS. La ventana own-retry permite que dos workers ejecuten antes de competir por la publicación; no es un lock sobre Kafka. Los timestamps del terminal se construyen en finalize (`startedAt=finishedAt`), así que no sirven para reconstruir duración original. Fuentes: [record](https://github.com/melisource/fury_rio-controlplane-kafka/blob/f74e856ef3de881e2d504c6cb1ced573681c1058/src/main/java/com/mercadolibre/rio_controlplane_kafka/idempotency/TriggerStatusRecord.java) y [guard](https://github.com/melisource/fury_rio-controlplane-kafka/blob/f74e856ef3de881e2d504c6cb1ced573681c1058/src/main/java/com/mercadolibre/rio_controlplane_kafka/idempotency/IdempotencyGuard.java).

## Semántica de retry/idempotencia

Los paths de deployment con operación válida y claim finalizan KVS antes de publicar terminal best-effort; si se pierde el result tras finalize, la redelivery del mismo ID se descarta sin republicar. GCP con `operation=null` publica `FAILED/INVALID_PARAMS` antes del claim: no deja terminal KVS y puede republicar ante repetición del mismo ID. Actions reservan publicación, envían y sólo entonces finalizan: publish fallido deja no terminal para takeover/redelivery. Publish aceptado con fallo posterior de finalize puede permitir duplicados; no garantiza exactly-once. KVS degradado permite procesar sin dedupe terminal. STARTED es best-effort. Ver [estados](../05-contracts/status-models.md#idempotencia-cp) y [runbook Kafka](../04-troubleshooting/kafka.md).

## Pivotes de troubleshooting

Correlaciona execution → UUID wire → provider/operación → efecto Kafka → KVS → result recibido. Si el topic cambió y Playmaker sigue pendiente, revisa publicación antes de crear otro deployment. Para GCP, comprueba primero transporte efectivo; para peek GCP, identifica la seam ausente. El detalle GET de history Playmaker puede resolver timeouts y disparar retries: no es una lectura garantizada sin efectos.

## Riesgos y datos sensibles

Ingress mutantes y peek directo no prueban provenance ni autorización de recurso a nivel app; gateway/mesh/subscriptions son `UNKNOWN_EXTERNAL`. Peek HTTP acepta destino outbound plaintext elegido por caller. No copies mensajes, brokers, offsets reales, `params`, `context`, outputs ni envelopes a tickets/prompts. Conserva sólo correladores mínimos, tipo/operación, estado, timestamp, conteo y clase de error sanitizada.

El bean GCP segment-bound requiere `rio.gcp.kafka.credentials.secret-segment`: prod/production la declaran y nonsite no. Tests de instancia no prueban `withSegmentId` efectivo ni despliegue; es gap de disponibilidad, no filtración demostrada. Mantiene el ID `kafka.gcp-secret-segment-wiring-gap`.
