## Selector fino de Flink

**Discrepancia de vigencia — 23 de septiembre:** el [diff canónico 21fdcfca→d196951d](https://github.com/melisource/fury_rio-controlplane-flink/compare/21fdcfcaf293796c00ab248e98c8d64c56bd757a...d196951dc6332769e9e60a2b54dfb19cbc60811c) elimina `controller/FlinkAppController.java`, `controller/DeploymentEventsController.java` y los publishers Stream/ComponentResult (paths bajo `src/main/java/com/mercadolibre/rio/controlplaneflink/`). `/flink/apps` —incluidos logs/start/stop— y `POST /events` están `ABSENT_ON_MASTER` en ese head. Sus referencias al SHA anterior son históricas: no invocar esas rutas como diagnóstico ni asumir el circuito Stream vigente. Manifiesto renovado a d196951d; los cuatro IDs retirados se conservan como guardrails históricos.

Al resolver las filas AWS logs o cleanup READY, usar los IDs legacy como guardrails de retiro, no como instrucciones para llamar al endpoint. La selección de tipos del CP también cambió de enum a configuración; verificar configuración efectiva antes de atribuir un ACK a soporte del tipo.

Después de elegir un intent Flink, recupera **una** fila. Cada bundle incluye los IDs que deben sobrevivir en la respuesta y un anchor decisivo; los detalles restantes se abren desde el catálogo o ledger enlazado.

Antes de responder aplica un gate mecánico de completitud sobre la **rama resuelta** de la fila elegida. Interpreta una lista simple como `required`; `o`/`según síntoma` como `one_of`; y `si`/`sólo si`/`para` como `conditional_if`. No unas las alternativas en un bundle mayor:

1. enumera todos los feature IDs y `edge.*`/`gap.edge.*` `required` de la rama elegida, exactamente un `one_of` justificado y sólo los `conditional_if` cuyo discriminador quedó probado; no los abrevies como “los gaps de Flink”, “las features Entity” o un wildcard;
2. abre y conserva los anchors decisivos de esa rama para los claims que lo requieren; un archivo alternativo útil puede agregarse, pero no sustituye al processor, poller, monitor, reconciler o consumer canónico;
3. escribe de forma explícita el dato que no se debe compartir y la mutación que no se debe ejecutar —por ejemplo `event body`, dump, prompt/SQL, URL/secreto, screenshot/cookie, replay, edición de KVS/registry o retry paralelo—; “usar evidencia sanitizada” no reemplaza esa enumeración;
4. cierra con el chequeo read-only y la condición exacta de escalamiento. Si falta uno de estos cuatro elementos, vuelve a la misma fila; no abras otro catálogo para compensarlo.

| Action `PENDING` | payload completo, republicación y edición de KVS | probar publish→binding→claim→terminal; escalar trigger confirmado sin claim CP |
| Polling UI vencido o stop sin terminal | retry/force-stop/delete | consultar action y provider; `READY` no autoriza cleanup |
| Delete pendiente | segundo delete y edición de KVS | separar `DEPROVISION` de stop y cubrir tanto recurso ausente sin terminal como recurso presente con terminal CP |
| Captura legacy AWS logs `200 null` | dump CloudWatch e invocación de ruta retirada | identificar versión/fecha; sólo en el baseline histórico tratar query/ventana como inconclusas, no como ausencia de error |
| GCP driver output | stacktrace, URL, variables y secretos | conservar sólo clase, timestamp e IDs; escalar exposición ya ocurrida |
| Candidato AI/SQL | prompt y SQL sensibles | validar/guardar y buscar execution por separado; escalar si no se puede validar sin contenido |
| UI vacía | screenshot sin redacción, cookies y redeploy | separar render/SSR/BFF/downstream antes de atribuir borrado |
| Datadog/Observability | API keys y configuración completa | comprobar flag, KVS/monitor y tags efectivos; código no prueba monitor desplegado |
| Publish runtime perdido | event bodies y edición/republicación de registry/KVS | comparar source, métrica, estado persistido e idempotencia; no prometer retry |

## Reglas de expansión

Si el pack requiere `pm.pipeline.history-detail`, no recomendar invocarlo como lectura garantizadamente sin efectos: puede resolver timeouts y disparar retries. Usar evidencia ya capturada o una lectura interna autorizada que no invoque el resolver; ver el [runbook de deployment](../04-troubleshooting/deployment-stuck-or-failed.md) y la implementación al SHA del [catálogo Playmaker](../09-feature-catalog/rio-playmaker.md).

Para falla de construcción de publishers BigQuery v1/v2 en Collector, recuperar `collector.bigquery.cross-segment-secrets` y el [runbook de entrega](../04-troubleshooting/signals-delivery.md#5-destino-y-recovery). Verificar segmento fuente/integración SDK y outcome sin pedir valores de secretos; no probar otro segmento ni replay como diagnóstico.

1. Usa síntoma e IDs para elegir, no similitud de nombres.
2. Para deployment, carga un solo CP al principio.
3. Si la ficha tiene confianza baja/media o está stale, abre código actual.
4. Si el flujo contradice la ficha, informa la contradicción y prioriza código.
5. Detente al identificar último límite confirmado y próximo chequeo.
6. Si la pregunta pide “qué soporta” o un endpoint/action exacto, usa primero `docs/09-feature-catalog/` y conserva el feature ID en la respuesta.
7. Clasifica maintenance, ramp-up, cuota y onboarding de alto caudal como `change/capacity`; no inventes un incidente ni un umbral.
8. Para UI, compara por separado grafo, desired/deployed, runtime y data plane antes de atribuir la causa al frontend.
9. Para “¿está disponible/estable/recomendado?”, distingue código existente, release publicada y política/versión aprobada.
10. En Flink, identifica primero `component_type`, provider y operación. La ruta AWS legacy de logs fue retirada: no usarla para ningún provider. No trates delete como action.
11. Si la UI dice “logs no disponibles”, verifica el contrato ASF→Playmaker antes de inferir que no hay logs o app.
12. Para SQL, separa contenido inline/workspace, definición guardada, execution, deployment terminal y runtime.
13. Para diseño cross-service, clasifica cada pieza como `REUSE_VERIFIED`, `MODIFY`, `NEW`, `ABSENT_ON_MASTER` o `UNKNOWN_EXTERNAL`; exige anchors bilaterales y no uses artefactos `SUPERSEDED`.
14. Para SDK Node, separa package instalado/loader de `master`: un `import` ESM no prueba server entry. Separa también invocación de `bodyValidator` de enforcement: retorno `false` no equivale a throw ni a `onValidate`.
15. Antes de GET/SSE SAGA, confirma identidad, ownership y binding componente↔correlation; conocer el correlador o incluir `component_name` en el path no acredita acceso.
16. Si una action cambia entre `COMPLETED` y `FAILED`, abre el consumer Playmaker y el binding antes del CP: KVS permite overwrite terminal y el último valor no prueba orden de llegada.
17. Para authz Entity, verifica `SCOPE`, profiles efectivos y ambos caminos permisivos. `ACME_BYPASS_TEAM_CHECK=false` y el guard `production` no descartan por sí solos el bean `local`.
18. Para Kafka peek, distingue la ruta normal Playmaker del endpoint directo: no uses un `brokers_url` alternativo para probar acceso; la validación sintáctica no demuestra allowlist de cluster ni TLS.
19. Antes de cerrar, compara la salida con el conjunto exacto de la rama resuelta (`required` + un `one_of` justificado + `conditional_if` probados): no reemplaces un anchor requerido por otro archivo parecido, no abrevies familias de IDs y escribe literalmente cada rechazo de seguridad/acción que aplique.
20. Para Python, `fury_signals-sdk-python` es canónico; `signals-sdk-sandbox-python` sólo acredita ejemplos y nunca reemplaza los contratos `sdk.python.*`.
