# Investigación avanzada sobre StrategyQuant X Build 142 para automatización de Custom Analysis

## Hallazgos clave

La conclusión más sólida es que **SQX sí permite automatizar la ejecución de proyectos por CLI, pero no encontré evidencia documental de un comando CLI nativo para compilar snippets Java desde `user/snippets/`**. La documentación oficial de `sqcli` enumera comandos para proyectos, databanks, herramientas, datos, ejecución de scripts, GUI remota y, desde Build 142, gestión de indicadores externos múltiples; **no aparece ningún comando tipo `-compile`, `-build` o similar para snippets**. Además, la propia documentación y varios ejemplos de instalación de snippets repiten el patrón **“Compile / Compile All” en Code Editor y luego reiniciar**, lo que apunta a que **el reinicio no sustituye la compilación del código fuente Java**. En cambio, para **JARs externos** sí se documenta explícitamente que basta con copiarlos a `user/libs/` y reiniciar SQX. citeturn11view0turn14search0turn14search1turn14search2turn10search0turn12search0turn12search10turn12search8turn12search6

También hay evidencia bastante clara de que, en el plano de GUI, **Custom Analysis tiene dos modos distintos**: uno **per strategy**, configurable en la pestaña **Ranking** de Builder / Retester / Optimizer, y otro **per databank**, disponible **solo** en un **Custom Project** como tarea **Custom analysis**. En el task de Custom Project, SQX permite elegir **Source databank**, **Target databank** y encadenar hasta **cuatro métodos** en el orden **per strategy → per databank → per strategy → per databank**. Eso calza muy bien con un pipeline Optimizer/Retest → Custom Analysis → exportación EA, sin hacer malabares raros. citeturn37view2turn37view1turn37view0

Sobre `ParametersSettings.setFromXML(lastSettings, rg.getStrategyXml())`, la mejor evidencia disponible hoy es incómoda pero útil: el artículo oficial sigue mostrando ese patrón, **pero un comentario posterior reporta en Build 142** el error **“Cannot load Parameters settings. Element ‘Optimization’ not found”**. No encontré una nota oficial de corrección para Build 142. Por tanto, para una implementación de producción, **yo no confiaría esa detección a `setFromXML()` en B142**. La alternativa más robusta es **pasar `symmetricVariables` como configuración explícita** —ya sea por fichero `.properties`, `inputArgs` o settings del snippet— y dejar una detección heurística solo como plan B. citeturn40view0turn39search1turn8search0turn43search0

Finalmente, **`StrategyParametersHelper` y `StrategyParametersHelperV2` no aparecen como clases nativas del API público de SQX**. La documentación los presenta como **helpers adjuntos al artículo**, dentro del paquete **`SQ.Utils`**, y el índice público de clases muestra una clase nativa llamada **`com.strategyquant.tradinglib.ParametersHelper`**, pero **no** `StrategyParametersHelper` ni `StrategyParametersHelperV2`. Traducción al cristiano: **no son built-ins de `com.strategyquant.tradinglib`**, sino utilidades de ejemplo que hay que importar/crear manualmente. citeturn8search0turn40view0turn27view0turn25view0turn26view2turn26view3

## Compilación en Linux headless

La documentación oficial de CLI describe `sqcli` como una interfaz de línea de comandos “fully featured” para interactuar con SQ/QDM, pero el listado oficial de comandos visibles incluye `-project`, `-databank`, `-tools`, `-symbol`, `-instrument`, `-data`, `-run`, `-gui`, `-waitfor`, `-deletefile`, `-execute` y `-exit`; desde Build 142 aparece además el uso de CLI para **external indicators** múltiples. En ese inventario no hay ningún comando documentado para “compilar snippets” del Code Editor. Por tanto, la respuesta más seria es: **no hay evidencia pública de soporte CLI nativo para compilar `user/snippets/*.java`**. citeturn11view0turn14search0turn14search1turn14search2turn14search9turn10search0

La segunda parte de la pregunta —si SQX autocombina y autocompila snippets al arrancar— tampoco queda respaldada por la documentación que encontré. De hecho, los ejemplos oficiales de Custom Analysis y snippets de codebase insisten en el flujo **“Compile / Compile All” y luego restart**. En paralelo, la documentación de “Using custom JAR libraries” sí dice expresamente que poner JARs en `user/libs/` y reiniciar los deja disponibles. Esa asimetría es importante: **reiniciar sí carga JARs**, pero **para fuentes Java de snippets la documentación sigue hablando de compilación explícita**. O sea, asumir autocompilación sería jugar a la ruleta con la prod; y pa’ qué, si ya hay suficientes gremlins en trading algorítmico. citeturn12search0turn12search10turn12search8turn12search6

Para un entorno realmente headless, hay un matiz útil: `sqcli -gui` levanta un **webserver** y expone la UI en el navegador en `http://localhost:8080`. La documentación lo presenta como una forma de acceder a la UI a través del navegador, partiendo de CLI. **No documenta explícitamente “compilar snippets por esa vía”**, pero sí describe que la GUI completa queda accesible remotamente. En la práctica, eso sugiere un workaround razonable si queréis mantener el flujo nativo de Code Editor sin escritorio local: usar `sqcli -gui` detrás de un túnel o reverse proxy y lanzar la compilación desde navegador. Lo dejo como **inferencia operativa razonable**, no como garantía oficial específica para compilación. citeturn13search0turn11view0

Si preferís una solución más limpia de CI/CD, **compilar externamente y desplegar un JAR a `user/libs/` es el camino más estable**. La parte medio mañosa es que **StrategyQuant no publica una guía oficial de external compilation con classpath mínimo exacto**. Lo que sí pude verificar por trazas y Javadocs es que el runtime usa al menos estos JARs propios: **`SQTradingLib.jar`**, **`SQDataLib.jar`**, **`SQGridLib2.jar`** y **`SQWebGUILib.jar`**; además carga JARs de terceros como **`jogl-all.jar`** y **`jetty-all-uber.jar`**. En logs de Linux también se ve que SQX usa un **JRE embebido bajo `j64`** y librerías internas como **`internal/jcef`**; además, el propio log muestra `java.class.path=` vacío y un **EmbeddedClassLoader**, lo que explica por qué la localización exacta del classpath no queda documentada de forma bonita. Mi recomendación práctica, por tanto, es **no mantener una lista manual “mínima”**, sino construir el classpath **con todos los JARs del árbol de instalación de Build 142** y dejar que `javac`/Gradle/Maven resuelvan contra todo el set instalado. Los nombres concretos verificados son los anteriores; **la lista exhaustiva y sus rutas exactas en disco no quedan documentadas en las fuentes públicas revisadas**. citeturn33search0turn34search0turn34search1turn34search2

En términos de plan de implementación, la receta más robusta sería esta: **compilar `EchoForgeAutomator` externamente**, empaquetarlo como JAR, copiarlo a **`<SQX>/user/libs/`**, reiniciar SQX y ejecutar el proyecto por CLI con `-project action=start`. Esa parte sí encaja bien con la documentación disponible: CLI gestiona proyectos y `user/libs/` es el punto de carga oficial de librerías personalizadas. citeturn12search0turn14search0turn11view0

## Integración en Custom Projects y binding de la clase

En la GUI hay que distinguir dos casos. Si queréis que el análisis sea **per strategy** y se ejecute como parte del ciclo de Builder / Retester / Optimizer, entonces **no va en un task de Custom Project**, sino en la pestaña **Ranking** del panel correspondiente. Allí el Custom Analysis se dispara **después de completar backtests y crosschecks y antes de guardar la estrategia en databank**. Eso sirve para filtrar o enriquecer cada `ResultsGroup` de forma individual. citeturn37view2

Pero para vuestro caso —trabajar con **plantillas `.cfx` preconfiguradas** y encadenar tareas— la pieza correcta es el **task “Custom analysis” dentro de un Custom Project**. La documentación oficial dice que los Custom Projects definen un flujo de tareas a la izquierda, ejecutadas **en el orden en que aparecen**, y que cada tarea puede usar databanks de **origen** y **destino**. La propia página de Custom Analysis añade que el task permite escoger **Source databank**, **Target databank** y cuatro slots de análisis encadenados. Por tanto, **para ejecutar inmediatamente después de Optimization o Retest**, lo correcto es poner el task de **Custom analysis justo después** en el flujo del proyecto y hacer que su **Source databank** sea el **Target databank** de la tarea previa. Esa es la forma “nativa SQX”, sin inventar duct tape. citeturn37view1turn37view2turn37view0

Sobre el binding de la clase concreta, la mejor evidencia viene del ejemplo oficial `WFPortfolio`. La documentación dice que crear un snippet Custom Analysis genera un `.java` en **`User/Snippets/SQ/CustomAnalysis`**, y en el constructor el snippet se registra con una llamada como `super("WFPortfolio", TYPE_PROCESS_DATABANK)`. Después, en la GUI del task, el propio artículo indica literalmente: **“Select the WFPortfolio in the custom task.”** Eso implica que **SQX lista en la UI el nombre registrado en el constructor** del snippet compilado. Por tanto, si vuestra clase hace algo equivalente a `super("EchoForgeAutomator", ...)`, una vez compilada y con SQX reiniciado, **debería aparecer en la selección del task con ese nombre**. citeturn37view3turn9search4

El detalle fino es que el **tipo del snippet importa**. `WFPortfolio` usa `TYPE_PROCESS_DATABANK`, mientras que el ejemplo `CAApplyOptimParams` usa `TYPE_FILTER_STRATEGY`. La documentación de Custom Analysis separa precisamente entre **per strategy** y **per databank**; por eso, la forma en que `EchoForgeAutomator` aparezca en el UI depende del tipo que paséis al `super(...)`. Si queréis exportar un EA por estrategia justo al terminar el Optimization/Retest, lo más natural es que sea **per strategy**; si queréis operar sobre el conjunto del databank completo, entonces **per databank**. citeturn37view2turn37view3turn40view0

## Estado de `ParametersSettings` en Build 142

Aquí toca ser brutalmente práctico. El artículo oficial de “Changing strategy parameters programmatically” sigue mostrando esta secuencia para deducir la simetría de variables: parsear `rg.getLastSettings()`, instanciar `ParametersSettings`, llamar a `setFromXML(lastSettings, rg.getStrategyXml())` y leer `parametersSettings.symmetry`. Formalmente, por tanto, **ese es el patrón recomendado por la documentación base**. citeturn40view0turn38search3

El problema es que la misma página acumula un reporte posterior, ya en contexto de **Version 142**, con el error **“Cannot load Parameters settings. Element ‘Optimization’ not found”**. No encontré en las fuentes públicas revisadas una corrección oficial, changelog o aclaración de que Build 142 lo haya arreglado. Entonces, la conclusión conservadora de producción es esta: **en Build 142 hay evidencia real de que ese método puede romperse en workflows concretos**, especialmente fuera del caso feliz del ejemplo original. No puedo afirmar “está roto siempre”, pero sí **“no es fiable como base única de detección en B142”**. citeturn40view0

¿Qué hacer entonces? La solución más robusta es **sacar `symmetricVariables` del terreno mágico** y tratarlo como **configuración explícita**. Tenéis ya un `.properties` dinámico; encaja perfecto ahí. Como alternativa, también existe `setInputArgs(String)` en `CustomAnalysisMethod`, así que SQX tiene un mecanismo para pasar argumentos a snippets, aunque la documentación revisada no detalla un flujo completo de uso para este caso. En cualquier caso, **forzarlo desde properties o inputArgs es mucho más estable que depender de `setFromXML()` en Build 142**. citeturn43search0turn40view0

Además, los ejemplos oficiales más recientes tampoco intentan “adivinar” siempre esa simetría. En “Running optimizations programmatically – update”, el ejemplo simplemente **fuerza `settings.symmetry = true`** al construir la configuración de optimización. Y en “Viewing and changing strategy parameters – version 2”, el helper V2 recibe explícitamente `boolean sameVariablesForLongShort = true` antes de recuperar valores. Eso no demuestra que la autodetección sea imposible, pero sí muestra un patrón de uso muy claro: **en código productivo, SQX tolera y hasta favorece pasar esa decisión de forma explícita**. citeturn39search1turn8search0

Si aun así queréis una detección automática **best effort**, el único enfoque con algo de sustento funcional que vi es una **heurística sobre nombres de variables**. La documentación de “Simple Optimization” explica que, sin simetría, aparecen nombres separados como `LongEMAPeriod` y `ShortEMAPeriod`; con “Generate symmetric variables”, esos nombres se colapsan a `EMAPeriod`, `EMAPeriod2`, etc. Por tanto, una heurística razonable sería inspeccionar variables o XML y tratar como **no simétrica** una estrategia que conserve pares `Long*` / `Short*`, y como **simétrica** una estrategia que use nombres compartidos. Pero eso es una **heurística de nombres**, no un contrato formal del API; yo la dejaría solo como fallback, nunca como fuente de verdad única. citeturn42view0

Mi recomendación final para este punto es simple: **Build 142 + producción = `symmetricVariables` explícito**, con prioridad `properties > inputArgs > heurística` y con la vía `ParametersSettings.setFromXML()` desactivada o encapsulada tras `try/catch` solo para telemetría. Eso os quita una clase entera de fallos fantasmas. Y esos son exactamente los que después te hacen mirar logs a las 3 AM con cara de “pero si ayer andaba”. citeturn40view0turn39search1turn8search0

## Disponibilidad real de `StrategyParametersHelper`

Aquí la respuesta es más nítida que una vela de 1 minuto cuando el spread está decente. La documentación oficial muestra `StrategyParametersHelper` y `StrategyParametersHelperV2` como clases dentro del paquete **`SQ.Utils`**, y además dice explícitamente que **ambas clases están disponibles como adjuntos del artículo**. Eso significa que se distribuyen como **snippet/helper de ejemplo**, no como clase base garantizada del core público. citeturn8search0turn40view0

El contraste con el API público refuerza esa lectura. En el índice público de clases de SQX sí aparece una clase nativa llamada **`com.strategyquant.tradinglib.ParametersHelper`**, pero las búsquedas sobre el índice público no devuelven coincidencias para **`StrategyParametersHelper`** ni para **`StrategyParametersHelperV2`**. Por tanto, **no hay evidencia de que exista una clase built-in llamada `com.strategyquant.tradinglib.StrategyParametersHelper` o `StrategyParametersHelperV2` en Build 142**. Lo nativo es `ParametersHelper`; lo otro es utilería de ejemplo que tenéis que llevar vosotros al proyecto. citeturn27view0turn25view0turn26view2turn26view3

## Recomendación de implementación para producción

Si tuviera que cerrar esto en un plan de prod sin dejar bombas de tiempo, lo haría así. **Primero**, trataría la compilación de `EchoForgeAutomator` como un proceso **externo a SQX**, generando un JAR y desplegándolo en **`user/libs/`**, porque eso es lo que sí está documentado de forma estable para headless. **Segundo**, usaría SQX solo para **cargar y ejecutar** proyectos ya configurados, mediante `sqcli -project action=start ...`, dejando la compilación fuera del runtime. **Tercero**, configuraría el flujo en un **Custom Project** con el task **Custom analysis inmediatamente después** de Retest/Optimization, enlazado por databank origen/destino. **Cuarto**, registraría el snippet con el nombre exacto que queréis ver en la UI, por ejemplo `super("EchoForgeAutomator", TYPE_FILTER_STRATEGY)`. citeturn12search0turn14search0turn37view1turn37view3

Para el problema de simetría, la política de producción debería ser tajante: **no usar `ParametersSettings.setFromXML()` como mecanismo principal en Build 142**. En su lugar, guardaría `symmetricVariables` en vuestro `.properties` o por `inputArgs`, y lo usaría tanto en la mutación XML como en el helper de parámetros. Dejaría la ruta `setFromXML()` como diagnóstico opcional dentro de un `try/catch`, registrando el fallo si aparece, pero sin bloquear la operación. Ese enfoque está mucho más alineado con la evidencia disponible que seguir la receta del ejemplo al pie de la letra y rezar. citeturn40view0turn39search1turn8search0turn43search0

Y sobre helpers, blindaría el repo con una **copia vendorizada** de `StrategyParametersHelperV2` o una versión propia mínima, junto con tests unitarios de parsing/mutación XML. Así evitáis depender de adjuntos manuales del Code Editor o de snippets “que alguien importó una vez y quedaron flotando”. En un CI/CD serio, eso es oro. citeturn8search0turn40view0

## Preguntas abiertas y límites de la evidencia

No encontré en las fuentes públicas revisadas una **lista exhaustiva y oficial** de los **JARs exactos y sus rutas en disco** para compilar externamente contra SQX Build 142. Sí pude verificar con alta confianza varios JARs core presentes en runtime —`SQTradingLib.jar`, `SQDataLib.jar`, `SQGridLib2.jar`, `SQWebGUILib.jar`— y observar que SQX usa un **EmbeddedClassLoader**, un JRE embebido `j64` y librerías internas como `internal/jcef`, pero **la documentación pública no expone un classpath mínimo oficial** para `javac`. citeturn33search0turn34search0turn34search1turn34search2

Tampoco vi una confirmación oficial de StrategyQuant diciendo “`ParametersSettings.setFromXML()` está roto en Build 142”; lo que sí existe es **evidencia directa de fallo reportado en la página oficial del ejemplo**, suficiente para considerarlo **no fiable** en un diseño de producción, aunque no para afirmar que falle en el 100% de los casos. citeturn40view0
