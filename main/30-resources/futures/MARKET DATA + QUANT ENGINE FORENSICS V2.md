# Resumen Ejecutivo  
En la práctica madura de mercado de capitales, los sistemas suelen designar una fuente primaria *por instrumento*, con esquemas explícitos para saltar al secundario si el primario falla. Por ejemplo, el protocolo MDP 3.0 de CME provee dos feeds UDP (Feed A y Feed B) que deben procesarse ambos; no se escoge un “primario” rígido sino que se recomienda consumir A y B simultáneamente como primera línea de defensa contra pérdidas de paquetes. Los proveedores de datos modernos (p.ej. Databento) ofrecen APIs con pautas formales de health-check, failover y rearreglo de huecos: incluyen heartbeats configurables, callbacks de reconexión con marcas de tiempo para detectar gaps, y mecanismos de *replay* o snapshots para rellenar datos faltantes. A continuación se contrastan estos patrones (Databento, CME MDP 3.0, etc.) con implicancia para Echo Futures.

# Modelos de Autoridad de Feed Observados  
- **CME MDP 3.0:** Los feeds A y B son *iguales* en autoridad; CME no define “Feed A es primario y B solo backup”: en cambio, recomienda procesar ambos porque a veces un paquete pierde en A y llega por B. En práctica, esto equivale a *duplicación activa*: ambos feeds comparten la carga de seguridad, ningún feed “autoriza” solo, sino que la unión de ambos garantiza cobertura completa. (FUSION: se reciben datos de ambos; si uno falla, aún vendrán datos por el otro). Sin embargo, no hay “mezcla de datos distintos” por instrumento: son fuentes clones a nivel de mensaje. No se permite, por ejemplo, tomar precio de A y de B indiscriminadamente para formar una única serie; se trata como un único sistema redundante.  
- **Databento:** Opera un único flujo normalizado (backed por múltiples DCs en AWS/NYSE etc.). En la API se identifica un *único proveedor* (no hay usuario final que cambie de fuente). El cliente puede elegir activar `reconnect_policy="reconnect"` para volver a conectarse automáticamente al mismo proveedor en caso de desconexión. No hay mezcla de diferentes vendors: cuando el feed regresa es el mismo canal lógico. La autoridad la tiene la única fuente de Databento para ese instrumento; no hay blending con otros feeds.  
- **Patrón general:** Muchos sistemas reales evitan el “blend” ambiguo de fuentes distintas. Si hay multi-feed (p.ej. A/B de CME), se la considera una *entidad común* de seguridad, no feeds heterogéneos. De esto se infiere que Echo debería designar por instrumento un feed primario bien definido. Si se habilita un secundario, es solo para conmutación tras fallo, no para mezclar datos formadores.  

# Detección de Salud y Staleness  
- **Heartbeats/Timestamps:** Es común usar latidos de corazón. Databento permite configurar `heartbeat_interval_s` (p.ej. 30s) y ofrece un método `is_heartbeat()`. Así el cliente sabe que la sesión sigue viva incluso sin ticks. Si el heartbeat se detiene, es señal de problema. CME no envía explicitamente “heartbeats” en UDP, pero cada paquete tiene secuencias implícitas. Se asume que la pérdida de paquetes activa (o ausencia prolongada de cualquier paquete) indica fallo.  
- **Secuencias:** Los feeds en CME llevan mensajes con estructura FIX Binary (SBE) que incluyen ID de paquete y número de secuencia. El cliente puede detectar huecos si ve saltos en esos contadores (aunque se respalda con TCP/Recovery). Databento no usa secuencias numéricas visibles al cliente, pero el callback de reconexión le entrega marcas de tiempo (`ts_event`) finales e iniciales, permitiendo detectar intervalos perdidos.  
- **Drift/Tiempo:** Se debe comparar *timestamp de evento* vs hora del sistema. Si llega mucho *ts_event* antiguo (o futuro), algo anda mal. Databento advierte que si el reloj local está fuera de rango, la sesión falla en autenticar (por seguridad). Los sistemas deberían validar internamente (p.ej. no aceptar ticks si el retraso supera cierto umbral).  
- **Desconexión clara:** Un feed detecta desconexión (socket cerrado). Databento manda un error o termina la sesión. El cliente idealmente intenta reconectar o marca el estado offline. CME UDP, al no tener conexión, puede requerir monitoreo en red (pérdida de IGMP grupo). En la práctica se emplean mecanimos a nivel de OS o de red colocalizada para recibir la señal de falla (por ej. instrumentos de monitoreo de la NIC).  

# Modelos de Failover  
- **Automático vs manual:**  
  - *Databento:* ofrece política `reconnect_policy` (e.g. `"reconnect"`) para reintentar automáticamente una conexión perdida. El cliente puede usar callbacks (`add_reconnect_callback`) para conocer exactamente cuándo se reengancha, con timestamps de gap.  
  - *CME MDP:* no tiene “auto-switch” en el API; en cambio, su enfoque es que el cliente siempre procese ambos A y B, mitigando así la necesidad de conmutar feeds. No existe por tanto una “transición automática” de un feed a otro: simplemente si A falla, el cliente sigue recibiendo todos los datos vía B. Las recomendaciones indican hacer failover (p.ej. pasar a TCP Recover) solo en situaciones de reposo o arranque, no en plena operación.  
  - *Otros sistemas:* Muchos mercados ofrecen una fuente alternativa (p.ej. transmisión por TCP o Websocket), pero usualmente hay que gestionar manualmente la reconexión al fallback. Por ejemplo, Databento también menciona reinicios planificados (mantenimiento de exchange) durante los cuales los clientes deben reconectar tras el evento.  
- **Condiciones de cambio:** En Databento, el propio disconnect dispara el reconnection policy; no hay condiciones complejas: pierde socket → intenta volver. En CME, la condición clara es pérdida de todos los paquetes por un tiempo (los routers IGMP pueden avisar). Un “fail trigger” típico: ausencia de nuevos mensajes durante cierto umbral (p.ej. varios segundos en trading activo). Para Echo, conviene definir un tiempo o conteo de heartbeats fallidos antes de iniciar failover.  
- **Evitar duplicados/reorden:** Al reconectar/regresar, pueden llegar datos repetidos. Databento previene esto proponiendo guardar el último `ts_event` y la cuenta de registros recibidos, y al re-subscribirse con replay *descartar* las duplicaciones explícitamente. En CME, si se usa el mecanismo de *Market Recovery*, las reglas de aplicación del snapshot se encargan de armar el estado limpio. Echo deberá implementar lógica similar: en replay, filtrar eventos cuya marca sea ≤ último procesado, y mantener conteos para evitar repeticiones exactamente iguales.  
- **Requisito de sincronización:** Tras cambiar de feed o reconectar, puede requerirse una *barrera de sincronización* antes de reiniciar la lógica. Por ejemplo, en Databento recomiendan almacenar todo el estado relevante (timestamp final por esquema) antes de reconexión, luego restablecerlo tras el replay. Echo deberá hacer similarmente: reconstruir indicadores/barra actual antes de permitir ordenes nuevas, basándose en la historia completa reaplicada.  

# Recuperación de Gaps  
- **Detección:** Los gaps se notan por secuencias faltantes o timestamps discontinuos. Databento emplea callbacks de reconexión que indican la brecha de tiempo exacta. Un patrón general es guardar la última hora y conteo y comparar al reanudar.  
- **Fuentes históricas:** La estrategia varía: Databento ofrece *intraday replay* de hasta 24h (o semanal en MBO), o un *Natural refresh* (resuscribir y tomar solo lo nuevo). CME MDP habilita un canal especializado “Market Recovery Feed” para snapshots: por ejemplo, un feed TCP para MBP/MBO completo, y loops de instrumento para definiciones. Muchos proveedores de datos primarios tienen servicios similares (TCP recovery o snapshots diarias).  
- **Shadow state vs historia:** Para indicadores/barras formándose, el gap recovery puede invalidar los valores intermedios. Al recibir datos atrasados, hay que reconstuirse: Databento menciona que el replay podría demorar, y en schemas de orden (MBO) prefieren enviar un snapshot en lugar de cada trade perdido. Echo debería incluir un modo de reconstruir barras: p.ej. si un close bar pudo haberse afectado por un trade perdido, vale más descartarla y recalcularla con los datos recuperados.  
- **Cierre de barra formadora:** En failover, la barra actual (formando) puede volverse inválida. Patrón típico: descartar la barra parcial y abrirla de nuevo con los datos recobrados (o marcarla truncada). Databento sugiere snapshots en MBO para evitar replays largos. Echo podría adoptar: usar *snapshot de libros* o *reactivar acumuladores* tras gap para reabrir la barra correctamente.  
- **Cuándo reanudar trading:** Normalmente, se espera a que el estado *caliente* esté listo de nuevo (e.g. barras e indicadores reconstruidos) antes de aceptar nuevas señales de entrada. Es prudente “pausar nuevos entries” durante la reconexión, pero se puede seguir gestionando órdenes/posiciones existentes para no “abandonar” el riesgo abierto. Estos flujos deben definirse claramente en la implementación de Echo.  

# Semánticas de Barra y Multi-timeframe  
*(Si bien el alcance original no pedía de nuevo bar semantics, se mencionan por completitud.)* Los sistemas difieren en cuándo considerarse “barra cerrada”. P.ej., en trading real, si llega un dato *muy tarde* (p.ej. después de varias barras nuevas), casi siempre se ignora para no violar la determinismo de backtest. Databento implica que al reconectar el esquema “Trades” construye tick a tick, y uno debe filtrar por timestamp para no duplicar. Para multitimeframe, el patrón es recalcular a partir de barras de base (ej. ticks → 1m → 5m). Si un feed failover corta el proceso, se debe evitar el *look-ahead* recalculando solo con datos confirmados. Por ejemplo, si falta un trade viejo, no se permiten modificar barras pasadas tras un retraso excesivo.  
En síntesis, los patrones indican: barras cerradas son definitivas; barras formadas parcialmente pueden reiniciarse tras gap; MTF debe reconstruirse con datos apropiados. Se evita reconstruir _posteriormente_ barras que ya se asumieron cerradas en backtests deterministas.  

# Patrones Fail-closed  
En un escenario de falla seria de feeds (p.ej. ambos primario y secundario caen, o no se puede garantizar frescura), muchos sistemas optan por suspender entradas nuevas: e.g. MSCI/Python frameworks suelen “pausar” y generar alertas. Databento sugiere reconectar automáticamente, pero no define qué hacer con señales de trading: eso queda al cliente. Por inferencia general, **Fail-closed** suele significar: detener nuevos orders (split de señal), pero seguir gestionando la exposición actual (e.g. salida de posiciones con rutas seguras). En Echo lo aceptable sería *no abrir nuevas posiciones* si no se demuestra continuidad de feed; se podría “eliminar señales vencidas” hasta restaurar conexión.  
No hay fuente directa consultada, así que queda como patrón: detener *entries* pero no liquidar todo, y priorizar alertar a operador.

# Requisitos Mínimos para D2  
- **Autoridad única por contrato:** Definir explícitamente un proveedor de datos primario para cada instrumento (ej. feed oficial de CME) y posiblemente un secundario (otro proveedor que consuma la misma fuente). El sistema debe saber qué leer de quién sin mezclar arbitrariamente.  
- **Health signals:** Implementar heartbeats o checks periódicos. Al menos, si no llegan eventos en X segundos, marcar dato stale. Registrar timestamp de último evento procesado globalmente por ticker. Un *feed healthy* debe ser monitoreado vía sequencias o latidos.  
- **Failover trigger:** Definir umbral: e.g. “si no recibo nuevos ticks/quotes en 5s en mercado volátil, iniciar proced. de reconexión o switch”. Para Databento-style, activar política de reconexión. Para CME, si pierde canal (por no recibir multicast), quizás intentar TCP Recovery (MDP).  
- **Gap recognition:** Debe registrarse el último ts_event por intervalo/marca de tiempo antes del fallo. Al restaurar feed, volver a pedir datos desde ese ts. Echo requiere almacenar (por cada stream: trades, quotes, etc.) la marca final y usarla en replay. Patrón Databento: guardar `ts_event` y conteo.  
- **Backfill mechanism:** Debemos decidir entre intraday replay (como Databento) o snapshot. Para instrumentos basados en trades, replay es natural; para libros grandes, snapshot. En D2: escoger para cada schema (por ej. MBP usar snapshot) o dejar opción condicional.  
- **Post-failover state:** Definir cómo reconstruir hot state. E.g. limpiar indicadores de la barra en curso. En transicion, reconstruir la barra actual desde el inicio (como reconstruir parcial).  
- **Feed authority en barras:** Debe conservarse la proveniencia (feed) mínima: etiquetas internas en datos o logs. No mezclar datos de distintos feeds para una misma barra sin cuidado (p.ej. marcar barra “cierre vía feed B tras falla de A”).  
- **Fail-closed policy:** Debemos decidir comportamiento de trading al perder feed. Como patrón: pausar *entries* nuevas; continuar *stops* y *gestion de posiciones abiertas*. Registrar esta política explicitamente para D2.  

# Casos Raros o Diferidos (Technical Debt)  
- **Triple feed/quorum:** No parece justificable introducir múltiples feeds con votación (no hay evidencia ni ROI alto). Se difiere sin necesidad para V1.  
- **Event-sourcing completo:** Aunque robusto, es sobreingeniería para V1. Anotar DT específico: “Agregar event-store solo si reaplicación pura se vuelve crítica”.  
- **Estado global distribuido:** Fuera de alcance; usar estados locales y confiar en restauración a partir de históricos. DT: sólo si la consistencia fuerte por cuenta se vuelve problema.
