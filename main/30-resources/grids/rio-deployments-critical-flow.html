Escenario observable

Muerte súbita de un control plane

BigQueue push

El CP recibe el trigger por HTTP.

ACK 200

El transporte considera entregado el mensaje.

Background

Un executor local comienza el trabajo.

Pod muere

El proceso y su memoria desaparecen.

Sin redelivery

BigQueue ya recibió el 2xx.

Playmaker espera

Timeout, falso fallo o execution varada.

Efecto no ejecutado

El trigger se perdió después del ACK. No existe recurso y ningún worker retoma el job.

Efecto parcial o completo

La infraestructura puede existir, pero Playmaker no recibe el terminal y luego descarta un resultado tardío.

Corrección estructural: persistir un inbox con deployment_id, estado ACCEPTED y lease antes de devolver 2xx.
05 / 08
Lo menos evidente

Cuatro trampas que los retries no corrigen

1

El timeout puede no existir

Si Playmaker cae antes del adapter, timeout_at sigue null y el scanner no encuentra el deployment.

2

El lock no reconstruye trabajo

Fury Lock evita dos avances simultáneos. No vuelve a emitir un BatchCompletedEvent perdido.

3

El KVS terminal puede bloquear recuperación

Si el CP guarda terminal antes de publicar, una redelivery puede ver “completado” y descartar el único mensaje recuperable.

4

STARTED es ambiguo

Fallar por reloj puede dejar un recurso huérfano. Reintentar sin reconciliar puede duplicar el efecto.
