6HTTP callback

Materializer hace POST a Playmaker: /deployments/{id}/logs.

7Normalización

Playmaker transforma el callback a DeploymentResultMessage.

Así funciona hoy para los tipos en esta ruta: el request original no queda abierto esperando infraestructura. El 201 acepta; la ejecución y los callbacks ocurren después.
Routing por verificar: el YAML base deja s3-bucket, gcs-bucket y catch-all en Materializer. gcp-kafka-topic no aparece en las rutas BigQueue base aunque Kafka CP lo soporta; falta contrastar configuración viva.

Fronteras de recuperación

Dónde puede quedar un gap

FronteraPor qué queda el gapEvaluación
MySQL → triggerLa transacción que crea el Deployment REQUESTED ya hizo commit. Después se ejecuta el listener AFTER_COMMIT en memoria. Si no llega al adapter, no hay trigger y timeout_at sigue null.Sin replay
HTTP 200 → trabajo del CPKafka, Flink y ClickHouse pueden responder 2xx antes de que el job exista durablemente; una caída elimina el executor local y BigQueue ya dio el mensaje por entregado.Aceptación no durable
Resultado → siguiente batchEl resultado se confirma en MySQL y el avance depende de otro evento Spring asíncrono. Fury Lock serializa; no reconstruye un evento perdido.Continuación no durable
Cómo evita Fury CP el gap efecto → publicación: QKVS conserva desired/observed y dos marcadores distintos. El reconciler adquiere un lease, ejecuta el efecto y guarda reportedDeploymentId; sólo después de publicar el resultado guarda publishedDeploymentId. Si quedan distintos, otro tick vuelve a intentar la publicación, incluso después de reiniciar.
timeout_at es el deadline con que Playmaker detecta un Deployment sin resultado. El adapter lo calcula antes de publicar; si nunca corre, queda null y el scanner de vencidos no ve esa fila.
06 / 06
Misma clase de problema, distintos cortes

La inconsistencia depende del momento de la caída

PLAYMAKER

Commit sin continuación

  1. La execution y los deployments quedan en MySQL.
  2. Playmaker muere durante el fan-out asíncrono.
  3. Ningún trigger, o sólo una parte, llega a los CPs.
  4. Las filas previas al adapter pueden quedar sin timeout_at.
CONTROL PLANE

ACK sin trabajo durable

  1. BigQueue hace push HTTP.
  2. El CP responde 200 y desprende background.
  3. La instancia muere antes de completar.
  4. No hay redelivery si la aceptación ya quedó confirmada.
RESULTADO / AVANCE

Efecto sin cierre

  1. El recurso puede existir y el resultado no publicarse.
  2. O Playmaker confirma el resultado y pierde el evento de avance.
  3. Un timeout puede cerrar FAILED antes de un resultado tardío.
  4. La execution queda incoherente o detenida.
El estado visible depende del corte: intención persistida sin trigger; sólo un subconjunto de componentes enviado; infraestructura creada sin resultado; resultado terminal sin siguiente batch. La pregunta común es qué estado durable permite reconstruir la próxima acción.
